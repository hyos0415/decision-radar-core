- claude-code 1건 · FastAPI 1건

**위 2절의 큰일은 하나도 test에 없다.** 큰일은 릴리스 노트가 아니라 HN · Reddit · 보안 공지로 들어오고(경보 그물 · 공식 보안 채널), 그 길은 관문 평가가 재지 않는다. 회귀로는 `2026-11-04-missed-items.md`의 5건 추적만 있다.

그래서 C1(보안 놓침 0건)은 「릴리스 노트의 일상 보안 수정에 라벨을 붙이나」를 재 왔다. 「큰일을 놓치지 않나」는 재지 않았다.

## 4. 「실행 의존성이냐 아니냐」는 위험의 축이 아니다

- 우리에게 가장 가까웠던 큰일 둘(LiteLLM 백도어 · Zod 악성 배포)은 **둘 다 전이 의존성 길**이었다. 「의존성이면 보안 아님」은 가장 위험한 경우를 버린다
- 반대로 k6의 「Go 의존성 보안 업데이트」 같은 줄은 일상 유지보수다. 무엇이 얼마나 위험한지 노트가 말하지 않는다
- 위험을 가르는 것은 **얼마나 위험한가**(악성 배포 · 실제 악용 · 원격 코드 실행 · 치명 등급 대 일상 수정)와 **우리에게 닿나**(우리 버전 · lockfile에 있나)다. 「그 기술 자체냐 의존성이냐」가 아니다

## 5. 드러난 틈

1. **전이 의존성 사고를 못 잡는다** — 경보 그물은 제목의 스택 · 런타임 이름만 본다. Zod는 lockfile에만 있다. 공식 보안 채널(OSV)이 lockfile 이름까지 보는지는 확인 안 함 `[확인]`
2. **사고 글과 대응 릴리스가 따로 논다** — eMudhra는 Electron 릴리스 노트로 대응이 왔지만, 무슨 일인지 알려 주는 사고 글(HN 1202점)은 못 잡았다. detect 초안에 「왜 중요한지」가 빠진다
3. **안전 평가에 큰일이 없다** — 위 1절의 모양(원격 코드 실행 · 실제 악용 · 치명 · 여러 글)을 가진 사례로 안전 세트를 따로 만들어야 큰일을 놓치는지 잴 수 있다

## 6. 다음에 정할 것 (사용자)

- 보안을 위험도로 나눌지 — 예: 1급(우리 것에 악성 배포 · 실제 악용 · 치명 원격 코드 실행 · 신뢰 붕괴 → 항상 · 즉시) · 2급(그 기술 자체의 보안 공지 · CVE → 주간) · 3급(의존성 올림 · 강화 · 권한 정리 → 목록만, 안전 기준 밖)
- 반론: 릴리스 노트는 심각도를 거의 적지 않는다. 3급으로 내린 의존성 CVE 올림이 실제로는 치명 OpenSSL 수정일 수 있다 — CVE 번호가 있으면 OSV에서 심각도(CVSS)를 조회해 급을 정하는 쪽이 「키워드」보다 낫다
- 안전 평가(C1)를 1급 · 2급 사례로 다시 만들지 — 2절의 실제 사고 + PHP2Shell을 우리 런타임으로 바꾼 변형
