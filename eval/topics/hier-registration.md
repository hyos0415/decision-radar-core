# v3 등록 — 제안 모드 + 피드백 루프 (2026-10-28, 응답 0건)

> 바꾸려면 지우지 않고 `변경 (날짜, 이유)`로 남긴다(규율 7). 규칙 변경은 아래 「검토 때」에만, 그 전에 이 문서에 적고 커밋한다.

## 왜 관문이 아니라 루프인가

- **틀렸을 때 비용은 화면이 정한다.** v1이 정밀도로만 거른 이유는 「틀린 계층이 글을 엉뚱한 부모 밑에 숨긴다」였다. 숨기지 않고 제안만 보이면 틀려도 비용이 작다
- **실사용 응답이 더 나은 정답이다.** 짝 판정 페이지에서 따로 고른 라벨보다, 실제 화제 카드를 보며 내린 수락·거절이 화제 탭의 쓸모(사람 맛)에 가깝다

## 무엇을 보이나

- 규칙은 v1 그대로 쓴다: `hier_methods.py` blob `fc8419a`의 P1 두 갈래(「앞부분」 · 「앞 2토막 공유」) + P2
  - v2 결과에서 「앞 2토막 공유」 갈래가 틀린 발화 2/2였지만, 결과를 보고 끄는 대신 **루프에서 갈래별로 잰다**
  - 제안 모드는 비용이 작아서 그 갈래의 데이터를 얻는 쪽이 낫다
- 상위 k에 보이는 화제마다 같은 주 전체 화제에서 부모 후보를 찾는다. 화제 안 글 짝 중 하나라도 규칙이 발화하면 후보가 된다. 후보가 여럿이면 발화한 글 짝이 가장 많은 쪽 하나만 보인다
- 화면은 **「~의 하위로 보임」 배지 + 맞음 / 아님**이다. 자동으로 숨기거나 접지 않는다
- 사용자가 **직접 묶기**도 할 수 있다: 「이 화제는 ___의 하위」로 부모를 고른다. 규칙이 놓친 하위를 잡는 유일한 신호다

## 무엇을 기록하나 (정답지와 같은 모양 — 그대로 다음 eval 셋이 된다)

```
{"week", "child_topic", "parent_topic", "pairs": [[a_item, b_item], …],   // 발화한 글 짝 (직접 묶기면 빈 목록)
 "rule": "P1-prefix" | "P1-shared" | "P2" | "manual",
 "verdict": "accept" | "reject" | "manual",                              // 아님 = 하위 아님 (같음·다름은 가르지 않는다)
 "by": "user-feedback", "at"}
```

- 사용자가 응답을 바꾸면 마지막 응답만 센다(이력은 남긴다). 응답하지 않은 제안은 세지 않는다
- 저장 위치·API 모양은 구현 티켓에서 레포 주인이 정한다(앱 데이터 폴더, git 밖)

## 검토 때 · 바꾸는 기준

- **검토 시점**: 갈래 구분 없이 응답이 30개 쌓일 때마다. 볼 수 있는 화제가 상위 k뿐이라 한 주 제안이 몇 개뿐일 수 있으므로, 4주마다 진행 수만 기록한다
- **보는 것**: 갈래별 수락률과 Wilson 95% 구간, 직접 묶기 수(재현율 하한 신호), 오프라인 정답지 회귀(보고만)
- **갈래 끄기**: 그 갈래의 응답이 15개 이상이고 수락률 Wilson **상한 < 0.5**이면, 그 갈래 제안을 끈다
- **자동 접기**: 그 갈래의 응답이 30개 이상이고 수락률 Wilson **하한 ≥ 0.8**이면, 그 갈래만 하위 화제를 부모 아래로 접어 보인다(펼치기 한 번, 제안 배지는 유지). 30개 중 29개쯤 수락해야 넘는다
- **규칙 고치기**(표시 목록 보강 · 새 갈래 등): 검토 때만 한다. 거절·직접 묶기 사례를 보고 고친 판은 **다음 30개 응답으로만** 판단한다 — 고칠 때 본 응답으로 고친 판을 재지 않는다
- 위 숫자는 모두 이 문서에 적힌 그대로 쓴다. 바꾸려면 `변경`으로 남긴다

## 알고 쓰는 한계

- **선택 편향**: 수락·거절은 규칙이 낸 제안만 평가한다. 재현율은 직접 묶기로만, 그것도 하한으로만 보인다
- **한 사람의 맛**이다: 응답하는 사람은 레포 주인 하나다. 「사람 맛」은 이 사용자의 맛이고 일반화하지 않는다
- 화면에 배지가 보이는 것만으로 판단이 끌릴 수 있다. 수락률은 「제안을 보고 동의한 비율」이지, 눈가림 정밀도가 아니다

## 구현 (이 문서 밖)

API(`TopicRow`에 부모 후보 · 응답 저장 엔드포인트, `schemas.py` → openapi → `gen:api` 한 PR)는 레포 주인 몫이고, 화면(배지 · 맞음/아님 · 직접 묶기)은 프론트 담당 몫이다(HYO-133 후속). 둘 다 구현 티켓 HYO-152(화제 계층 제안 모드 + 피드백 루프)에서 다룬다.

### 변경 (2026-10-28, 응답 0건 — 화제 단위로 합치는 규칙, 사용자 결정)

구현(HYO-152)을 W43 상위 120 화제에 돌려 보니 제안이 6개 나왔다. 그중 둘은 위 「무엇을 보이나」의 합치는 방식에서 생긴 문제와 규칙 P2의 약점이었다. 응답을 받기 전에 정한다.
- **고친다 — 부모 자체를 담은 화제**: 자식 화제 안에 부모 글과 모델 이름이 같은 글(대소문자·구분자 무시)이 있으면, 그 부모 화제는 후보에서 뺀다(양방향 발화와 같은 취급). 예: `LiquidAI/LFM2.5-24B-A2B` 화제는 원본 모델 글과 GGUF 글을 함께 담고 있다. GGUF 글 하나 때문에 화제 전체가 블로그 글 「LFM2.5-24B-A2B: Built for …」의 하위로 제안됐다. 규칙(`pipeline/topic_hier.py`)은 바꾸지 않았다
- **두고 루프에 맡긴다 — P2 이름 뽑기**: 「model : MTP support for Mellum2.1 …」 제목에서 이름이 `model`로 뽑혀, 「using … models」·「run any GGUF model」 글이 그 하위로 제안된다. 규칙 취향의 문제라 고치지 않는다. 「아님」 응답이 P2 갈래의 거절 데이터가 된다
- 이 결정은 W43 제안을 보고 내렸다. 갈래별 수락률은 이 변경 뒤의 응답으로만 센다
