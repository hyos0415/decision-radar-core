## 1. 왜

GPT-6.1 Terra(10/26 출시)를 제품이 네 번 받아 놓고 한 번도 보여 주지 못했다 (HYO-168 표). 원인은 두 겹이다.

- **물음이 하나뿐이다.** 관문은 「내가 쓰는 **이름**에 급한 일이 생겼나」만 묻는다. 「내 **자리**에 들어올 새 후보가 나왔나」를 맡은 체가 없다 — Terra · Haiku 5.5 · GPT-6 Rosalind가 다 여기서 빠졌다. 후속 모델 규칙(HYO-129)은 같은 계열 + 높은 버전만 본다
- **보이는 칸이 너무 적다.** 관문이 남긴 것은 주 16~31건(W43~W45)인데 전체 5칸만 detect로 가고, detect가 그중 초안 1건쯤 쓴다. 사용자는 주 1건만 본다 — 걸러진 게 맞는지 확인할 창이 없다 (사용자 11/4: 「한두 개만 가져오는 것 같아서 아리까리하다」)

관문을 느슨하게 하면(예: minor도 남김) Terra 하나 얻고 patch 수십 건이 같이 온다. 그래서 체를 풀지 않고 **질의마다 자기 몫을 가져온다** (사용자 11/4: 「관문 당 결과를 가져오는 식으로」).

## 2. 모양 (사용자 결정 2026-11-04)

| 칸 | 무엇 | 규칙 |
|---|---|---|
| **항상** | 보안 공지 · 우리 버전 EOL · 모델 은퇴 | 관문이 이 종류로 남긴 것은 **몇 건이든 무조건** 보인다. 순위·몫 밖 (사용자: 「아묻따 항상」) — C1(안전)을 더 세게 |
| **기술 질의** | 스택 기술마다 그 기술에 일어난 일 | 관문이 남긴 것 중 **기술마다 top-3** (등급 → 심각도 순, 지금 정렬 키 그대로). 「항상」 항목은 몫을 쓰지 않는다 |
| **자리 질의** | 자리(스택의 모델 자리)마다 들어올 새 후보 | 자리 적합도 **2점 이상**(0~3) 중 **자리마다 top-3**. 없으면 「없음」 — top-k는 늘 채우므로 문턱이 소음을 막는다 |

- **보이는 것(목록)과 초안(detect)을 나눈다.** 목록 = 세 칸 전부(주 10~20개 예상, 질의별로 묶어 한 줄씩 — 훑는 데 2~3분, 항목마다 승인·거부 없음). detect 입력 = 「항상」 전부 + 질의마다 **1위만** — 초안은 결정이 필요한 일이라 많으면 안 된다. 목록의 2·3위는 사람이 보고 capture할 수 있다
- **변경 (2026-11-04 오후, 사용자 — 얼린 W44 · W45에 저장된 관문 판정으로 오프라인 비교 뒤)**: detect 입력을 넓힌다. 「놓치는 게 소음보다 더 거슬린다」
  - **「항상」**: 목록에는 그대로 전부, detect로는 **(패키지 × 줄)마다 가장 새 버전 1건**. 줄 = 관문이 기록한 우리 줄 / 다른 줄(`scope.release_line`, HYO-148 — 판정에는 여전히 안 쓴다) — 기록이 없으면 제목 버전의 주 버전(0.x는 부 버전). 벤더 문서처럼 버전이 없으면 접지 않는다. 그대로 전부 보내면 W44 23건 중 대부분이 같은 보안 수정의 다른 줄(Electron 42 · 43 · 44 · 45-beta, langfuse 3.x · 4.x, uv ×2)이었다. 「기술당 1건」(안 A)은 대표를 정렬 키(등급 → 심각도 → id)로 뽑아 v42 · v3 · v1 같은 옛 줄이 남고 우리 줄(Electron 45 정식 · langfuse 4.70 · 4.71 · pydantic v2.14.2 · langchain 1.4.8)과 다른 문서(Anthropic release-notes)가 빠져서 기각 — 빠지는 16건 중 「높음」 6건
  - **기술 질의 · 자리 질의**: **top-3 전부** detect (목록 = detect). 자리 1위만이면 Haiku 5.5(W42 조건 추출 2위 · 관문 분류 3위)와 Terra(W44 관문 분류 2위)가 목록에만 뜬다. 기술 질의 2 · 3위에는 같은 기술의 다른 문서(W45 claude-sonnet-5-5: model-deprecations · release-notes)가 있다
  - 오프라인 건수(지금 코드 · 저장된 판정): detect W44 **24** · W45 **17**, 목록 28 · 18. W44 판정은 HYO-148 전 코드라 줄 기록이 없어 Electron 다른 줄이 주 버전마다 남는다(줄 기록이 있으면 약 22). W46부터는 diff 쪼개기(doc-pipeline §4-5)로 문서 항목 구성이 달라진다
- 목록에 있었는데 초안이 안 된 것 · 목록에도 없었던 것을 가를 수 있다 → 「놓친 것」을 어디서 놓쳤는지 잰다
- 결정표(등급 × 변화)와 관문 판정은 그대로다. 바뀌는 것은 남긴 뒤의 **고르기**(전체 5칸 · 기술당 1칸 먼저 → 질의별 top-3)
- **변경 (2026-11-13, 사용자 「바로 풀어버리고」 — HYO-187 PR)**: **기술 질의는 상한 없음** — 관문이 남긴 것은 기술마다 전부 목록 = detect(`policy.TOPK = None`). 「항상」 칸과 접기는 그대로다(자리 질의 상한은 §3 변경 2026-11-12에서 이미 없앴다).
  - 얼린 W43~W46 관문 결과에 다시 걸어 보니 3위 밖으로 잘린 것은 FastAPI 연속 릴리스 8건(W43 0.148~0.150 · W44 0.150~0.162, 전부 breaking)뿐이었다.
  - 정렬 키가 등급 → 심각도 → id라 잘릴 때 옛 버전(0.145~0.147)이 남고 새 버전이 잘렸다. 상한이 없으면 이 순서 문제도 결과에 영향이 없다.
  - detect 입력 변화: W43 13 → 16 · W44 22 → 27 · W45 · W46 그대로(잘린 것 0). 관문 판정 · 「항상」 접기는 그대로라 늘어나는 것은 같은 기술의 연속 릴리스다.

## 3. 자리 질의 (새 체)

**자리 프로필** — ADR repo `radar-slots.yaml` (사용자 결정: 한 곳 · 스킬도 같은 파일을 읽을 수 있다). 자리마다 레포 · 하는 일 · 지금 모델 · 조건. 첫 버전은 각 레포 CLAUDE.md 「외부 모델·서비스」에서 뽑았다(사용자 11/4 「다 맞다」).

**새 모델 소식 모으기 (스크립트 — 결정론)**: 어느 레인이든
- 벤더 changelog 블록 중 출시 문구(Released · Introducing · now available · generally available)
- AWS Bedrock What's New 피드 항목
- HN · Reddit 중 제목에 모델 이름 꼴이 있거나 모델·가중치 글로 보이는 것 (HN은 점수 문턱)
- Reddit LocalLLaMA 「New Model」 flair · Hugging Face trending 모델

**판정 (모델 — 구독 CLI 한 세션)**: 후보 목록 + 자리 프로필 → 후보마다 「새 모델·서비스 출시인가」 · 맞는 자리 · 적합도 0~3 · 한 줄 이유. 스크립트가 id · 스키마를 검사한다. 원본 응답을 남긴다 (`pipeline/out/<주>/slots-raw.json`). 엔진은 `claude -p`(HYO-99와 같은 구독 설정 — API 키를 지운다). codex 갈래는 HYO-169

**순위**: 자리마다 적합도 → 인기(같은 출처 안 순위) → id. 문턱 2점.

**변경 (2026-11-12, 사용자 — 자리 질의 v2: 「무슨 제품을 쓰냐보다 그 제품이 내 프로젝트에서 어떤 역할을 하느냐」 · 「건 수 늘어도 돼, 놓치지만 않으면」)**: 위 모으기 · 판정 · 순위를 아래처럼 바꾼다. 프로필이 `version: 1`이면 예전 그대로 돈다.
- **역할 프로필 v2** (ADR repo `radar-slots.yaml`): 조건을 **must**(역할 조건 — 못 지키면 최대 1)와 **now_via**(지금 쓰는 방식 — 깎지 않고 「바꾸려면 필요한 것」 `switch` 메모로)로 나눈다. **kinds**(LLM · 판정 모델 · 분류기 · 임베딩 모델 · 리랭커)를 적는다. 역할 12개 — 관문 등급 재분류 · 검색 임베딩 · 희소 검색 · 리랭커를 더했다
- **모으기 넓히기** (`WIDE_CANDIDATES`): HF **작업별 순위**(분류 · 토큰 분류 · 임베딩 · 문장 유사도 · 순위 매기기 …) 10위 안 · LocalLLaMA 주간 30위 안은 출시 낱말이 없어도 · LocalLLaMA News 꼬리표
- **판정**: 파인튜닝 · 증류 모델도 새로 내놓은 것이면 출시(쓸 만한지는 적합도가 가른다). 답에 `model` 이름
- **순위**: 역할마다 상위 3 상한 없음 — 2점 이상 전부(detect로), 같은 `model`은 한 줄(`also`). **최고 1점인 출시는 「확인 필요」**(`slots.json` `check`, detect 아님) — 목록 · 화면 칸은 API 계약 변경이라 후속
- 엔진은 그대로 `claude -p` **Sonnet 5.5**(`--model`로 바꿀 수 있다). Haiku 5.5 비교(같은 W41 · W43): 놓치는 것은 비슷하나 W43에서 2점을 거의 주지 않고(detect 2건) 「확인 필요」가 49줄로 시끄러웠다 — 주 1세션이라 Sonnet을 둔다
- 확인 (얼린 W41 · W43, Sonnet 2회씩 · 모델 호출 6세션 + Haiku 2세션): W41 판정 모델 물결 소식 42건 중 보이는 것 2 → 23(남은 것은 대부분 토론 글) · W43 보이는 소식 7 → 23(빠진 것 0). 「확인 필요」까지 보이는 것으로 치면 두 실행이 W41 51/55 · W43 53/57 겹친다. detect 입력이 역할 질의에서만 주 15~35건 — 관문 몫까지 detect 한 번에 소화되는지는 W47에서 본다

**변경 (2026-11-21, 사용자 — HYO-244)**: W47 재실행에서 `hf-model:LiquidAI/LFM3-1.7B`가 「언어 정보가 없어 한국어 확인 필요」로 1점(확인 필요)이 됐다. 얼린 소식 `meta.tags`에는 `ko`를 포함한 9개 언어 태그가 이미 있었다 — HF 소식은 `text`가 비어 있고 판정 입력은 본문 300자만 받아 모델이 태그를 못 봤다. 고친 것: (1) 판정 입력에 후보마다 코드가 태그·제목에서 뽑은 `langs`(ISO 639-1 · `multilingual`) · `base_model`(한정 없는 첫 `base_model:` 태그) · `size`(제목의 `1.7B` · `E2B` 꼴, 분명할 때만)를 붙인다. (2) 판정 답의 match에 선택 칸 `missing`(`language · size · runtime · license · other` — 정보가 모자라 낮췄을 때)을 둔다. 옛 raw는 이 칸이 없어도 그대로 통과한다. (3) **코드 규칙**: 자리가 `lang: ko`(radar-slots.yaml, 소문자 두 글자)를 적었고, 그 자리의 1점이 `missing == ["language"]`이면 태그로 상태를 본다 — `ko` · `multilingual` · 언어 코드 3개 이상이면 `pass` → 2점으로 올리고(이유에 `· 언어: HF 태그로 확인(…) — 코드가 2로 올림`), 태그가 `en` 하나뿐이면 0점으로 내리며(`· 언어: 영어 전용 태그 — 코드가 0으로 내림`, 그 자리 matches에서 빠진다), 언어 태그가 없으면 그대로 둔다(Raon-1-nano). `missing`에 다른 항목이 같이 있으면 올리지 않는다. `lang`이 없는 자리는 건드리지 않는다. 고친 것은 `slots.json`의 `lang_adjusted`({id, slot, from, to, why})에 남는다. 코드: `pipeline/slots.py` `derive_fields` · `lang_status` · `apply_lang`.

### 변경 (2026-11-13, HYO-187 — 관심사 질의 추가, 사용자 결정)

위 세 칸은 그대로 둔다. 네 번째 길 **관심사 질의**를 더한다. 자리 질의는 모델만 보기 때문에, 모델이 아닌 새 기술(검색 기법, 그래프 도구, 에이전트 런타임, eval 도구, OCR 등)은 레인 B 키워드 순위로만 들어왔다. 그런데 그 순위는 목록에도 detect에도 가지 않았다.

| 단계 | 무엇 | 근거 |
|---|---|---|
| 1. 검색 | 관심사마다 **BM25**(파이썬, ES·GPU 없음)를 영어 낱말 질의(영어 topic + 별칭 + 예시)로 돌려 레인 B 후보 **상위 60** | `eval/interest/results-v2.md`: 네 주 · 질의 56에서 BM25 0.577 ≈ 하이브리드 + 리랭커 0.604(차이 CI가 0을 걸침) > KURE 0.508 > 시멘틱 서치 0.409(문장 질의도 0.401) · 지금 키워드 매칭 0.374. 파이썬 BM25는 0.564로 ES BM25를 재현(상위 30 겹침 82%). 상위 60은 사용자 11/12 「상위 60으로」 — 이름이 그대로 나오는 정답이 30 밖으로 밀렸다 |
| 2. 판정 | 구독 `claude -p`로 관심사마다 한 세션. 등급 0~2(eval 정답과 같은 규칙, 2 = 특정한 새것) | eval 판정 규칙 — Opus 1차 검수에서 0과 1 이상 일치 29/30 |
| 3. 주 10건 | 구독 `claude -p` 한 세션이 새것 중 「직접 실험해 볼 만한 것」을 최대 10건, 중요한 순서로 고른다. 번호 · 상한 · 겹침은 코드가 검사하고, 실패하면 코드 규칙(관심사마다 검색 1위, 프로필 우선순위 순)으로 대신 고른다. 관심사 예시(「이미 아는 것」) 자체를 다룬 글은 고르지 않는다 | 사용자 11/13 「그냥 10개 정도」 — W46에 새것이 161건이었다 |

- detect 입력 = 주 10건(kind `new_technology`). 나머지 새것과 「주제만」은 `interest.json`에 남긴다(놓친 것을 나중에 가를 수 있게).
- 목록(`list.json`) · 화면에 관심사 칸을 붙이는 것은 다음 PR이다(`WeekList` 계약 · OpenAPI · 프론트가 함께 바뀐다).
- 주간 사슬: `slots` 다음 · `feed` 앞에 `interest` 단계. 실패해도 계속 간다. 주당 구독 세션은 관심사 14 + 고르기 1이다.

실사용 지표(검토율 · 행동률, 비교 프로토콜 §7 G4)는 **초안** 기준이라 정의는 그대로다. 다만 detect 입력이 5개에서 「항상」(접은 것) + 질의별 top-3으로 바뀌어(§2 변경) 초안 수가 달라진다 — `real-use-changes.md`의 날짜로 나눠 보고한다. 목록을 연 기록은 행동 로그에 따로 남긴다(지표 밖). 어느 지표를 더 볼지는 판정 전에 사용자가 고른다 (11/4 「찬찬히 고르면 되겠고」).

## 6. 화면 · API

백엔드가 주마다 목록(세 칸 · 질의별 묶음)을 내보낸다 — 계약은 `desktop/backend/schemas.py`. 화면은 별도 세션이 병렬로 만든다 (사용자 11/4).

**detect 판정 붙이기 (2026-11-05, 사용자 나안 · HYO-171)**: `list.json`은 수집 PC가 만들고 detect는 맥이 돌린다 — 파일에 되돌려 쓰지 않는다. `GET /week-list`가 읽을 때 이 기기의 detect 실행 기록(`runs.jsonl`) 중 **그 주 입력으로 끝까지 돈 마지막 실행**을 찾아 `to_detect` 줄마다 `detect`(초안 · 기존 결정 · 버림 · 대상 밖 · 초안 실패 · 판정 없음)를 붙이고, 그 실행을 `detect_run`으로 알린다. 아직 안 돌았으면 둘 다 null(화면은 「초안 후보」). 판정 칸이 겹치면 초안 > 기존 결정 > 대상 밖 > 초안 실패 > 버림 (`service._detect_verdicts`).

**출처 건강 한 줄 (2026-11-05, HYO-172)**: 수집 PC가 얼릴 때 주차 폴더에 `source-health.json`을 쓴다 — 실사용 `<radar-snapshots>/<주차>/source-health.json`(`detect/` 옆), 개발 예시 `<data>/lists/<주차>/source-health.json`(list.json 옆). `GET /week-list`가 읽어 `source_health`로 싣고, 이상(`problems`)이 하나라도 있으면 「이번 주」 머리말 아래에 `line` 한 줄을 경고색으로 보인다(마우스를 올리면 출처별 이유 · N주째). 파일이 없거나(옛 주차) 못 읽으면 null이고 한 줄도 없다 — 목록은 막지 않는다. 모르는 키는 무시한다.
