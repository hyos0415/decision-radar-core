# Retrieval Arena 설계

> 초안 v0 · 2026-09-29 · 상위 문서: `overview.md` (M3, G1·G2)
> **가설 칸은 비어 있다** — 사용자가 사전 등록한다. 이 문서는 틀(무엇을, 무엇으로, 어떻게 공정하게)만 정한다.

## 1. 질문

> **이 태스크(기술 결정 기록의 발견·영향 매칭·재검토)에 최적인 검색 방법은 무엇인가 — 질의 유형별로, 규모별로.**

단일 승자를 고르는 게 목표가 아니다 (제안서 §12: "Exact → BM25, Impact → Hybrid + Internal Context" 같은 결과가 나오면 라우터로 간다).
세 가지를 답한다:

1. 질의 유형(A\~K)마다 어느 전략이 이기는가 → 라우터 설계의 입력
2. 규모가 커질 때 **Full Context(= 스킬 방식)가 어디서 무너지고**, 그때 무엇으로 넘어가는가 (G1)
3. 이기는 전략의 **구축 비용**(시간·크기·LLM 비용)이 그 이득만큼의 값을 하는가 (retrieval-arena 판정의 남은 틈 c)

**변경 (2026-10-02, 사용자 결정 — 결과 0건)**: C-DOC을 「실제 대상 기술 문서」(이미 스택에 있는 기술)로만 두면 B·D·H 질의(정답 = 아직 쓰지 않는 기술)의 정답 문서가 코퍼스 밖에 있다. C-DOC은 **수집 파이프라인(`doc-pipeline.md`, 에픽 E9)의 주간 스냅숏과 거기서 확인한 1차 출처**로 채운다. 코퍼스 버전 = 스냅숏 버전. 규모 티어(T1·T2)를 스냅숏 누적 주 수로 다시 정의할지는 HYO-32 착수 때 정한다(`doc-pipeline.md` §11 D6).


### 청크 정책 `chunk-policy@v1` (2026-09-29 결정, 상한 값은 미정)

파일마다 규칙을 손으로 만들지 않는다 — **파일 유형 → 규칙** 표 하나를 정책으로 고정하고 버전을 매긴다. 정책이 바뀌면 코퍼스 버전이 바뀐다.


| 파일 유형        | 규칙                                     | 상한 초과 시                          |
| ------------ | -------------------------------------- | -------------------------------- |
| ADR          | 파일 하나                                  | 헤딩으로 자르고 frontmatter 요약을 각 조각 앞에 |
| 문서 (md·html) | H2/H3 헤딩                               | 문단 경계에서 자른다. 표는 행 단위로 자르고 머리행 반복 |
| CLAUDE.md    | 헤딩                                     | 문서와 같음                           |
| manifest     | 파일 하나                                  | —                                |
| 코드           | 함수 (AST). 메서드는 클래스명 접두, 함수 밖 코드는 모듈 조각 | 함수 내부를 줄 단위로                     |
| 기타           | 고정 길이                                  | —                                |


- **모든 조각 앞에 위치 경로**("문서 제목 > H2 > H3" / "경로 > 클래스 > 함수"), **메타데이터(버전·날짜·source\_type) 상속**
- **상한 = 전략들이 쓰는 모델 중 가장 짧은 입력 한도 이하.** SPLADE-v3(BERT)는 512토큰까지만 읽는다 — 상한이 더 크면 SPLADE만 잘린 조각을 보게 되어, 졌을 때 방법 탓인지 잘림 탓인지 가를 수 없다
- 정책마다 **통계를 남긴다**: 조각 수 · 길이 분포 · 상한으로 잘린 조각 수. "파일마다 성격이 다르다"는 변수를 숨기지 않고 드러낸다
- 청크 방식 최적화는 이 Arena의 질문이 아니다 — 정책을 고정하고 전략을 비교한다
- 커뮤니티 신호(trend-radar)는 **코퍼스가 아니다** — 후보를 올리는 입구일 뿐, 검색 결과로 근거가 되지 않는다(R2)
- **청크 방식은 교란 변수다.** 코퍼스마다 한 가지로 고정하고, 모든 전략이 같은 청크를 받는다(그래프 전략은 청크 대신 노드). 청크 방식을 바꾸면 코퍼스 버전이 바뀐다
- 청크 방식은 사용자가 사전 등록 때 정한다 (§6)

### 버전과 규모 티어

코퍼스는 `C-ADR@v1`처럼 버전을 붙여 동결한다. 버전이 바뀌면 모든 전략을 다시 돌린다(비LLM 전략은 재실행 비용이 거의 0).


| 티어  | C-ADR                      | C-DOC       | 목적                        |
| --- | -------------------------- | ----------- | ------------------------- |
| T0  | 실제 ADR 전부 (수\~수십 건)        | 실제 대상 기술 문서 | 실사용 규모                    |
| T1  | 50                         | ×10         |                           |
| T2  | 500                        | ×100        | Full Context가 버거워지는 구간 후보 |
| T3  | (선택) Full Context가 불가능한 규모 |             | 컨텍스트 한도 밖                 |


- T1 이상의 ADR은 **합성**이다. 실제 기술 목록에서 결정을 늘려 만들되, 합성 ADR의 gold 정답은 합성 규칙에서 나오므로 **실제 ADR 질의와 따로 집계**한다
- 합성은 평가 대상 모델과 다른 회사 모델로 만든다 — 같은 모델이 만들고 검색하면 표현이 겹쳐 유리해진다

| -------------- | ------------------------------------------------------ | -------------------------------- |

## 4. gold set

- **gold set을 만들기 전에 `eval-precondition` 모드 1로 전제를 확정한다** — 기존 eval(`eval/precondition-sheet.md`)과 같은 절차. 특히 "정답이 유일한가"(CLAUDE.md 규율 2: F1 가격 페이지 모호함)
- 판정 단계: 관련(2) / 부분 관련(1) / 무관(0). nDCG를 쓰려면 등급이 필요하다
- 초안은 LLM(평가 대상과 다른 회사)이 만들고 **사람이 확정**한다. 확정은 사용자가 한다 — 정답을 정하는 쪽이 전략을 짜는 쪽과 같다는 점은 한계로 기록한다
- 분할: **dev**(전략 튜닝용, 들여다봐도 됨) / **test**(봉인 — 사전 등록된 최종 비교에서만 연다)
- 버전: `gold@v1`. 질의를 추가하면 버전이 바뀐다. test에 질의를 보탤 때는 새 전략을 본 뒤가 아니라 **등록 시점 전에**

**변경 (2026-10-12, 사용자 결정 — 결과 0건): gold@v1 전제 확정** — 전문은 확정 시트 `eval/arena/gold-precondition-sheet.md`(+ `.json`). 요점:

- **판정 단위 = 문서**(C-DOC 항목 id · ADR 파일 · C-CODE 파일). 청크 정책과 무관하게 지금 라벨한다. 채점 때 전략의 청크 순위를 문서로 올린다(문서마다 최고 순위 청크 하나)
- **C-DOC@v1 = `corpus@2026-W41` 전체 2,290건, reddit·hn 포함 — 단 커뮤니티 항목의 등급 상한은 1.** 위 §2의 「커뮤니티 신호는 코퍼스가 아니다」를 이렇게 바꾼다: 검색 대상(색인)에는 넣되 **근거(등급 2)는 1차 출처만**(R2 유지). 실제 detect가 보는 소음을 견디는지도 잰다. **+ 보충 `source-hints@2026-10-12`**(ADR web 재검토 조건의 1차 출처 6건 — W41엔 J 판정 근거가 없었다. doc-pipeline의 C-DOC 정의 「스냅숏 + 1차 출처 확인」과 같은 경로)
- **정답 집합은 GPT 전수 스크리닝으로 만든다** — 질의마다 전체 문서를 평가 대상과 다른 회사 모델이 판정하고, 후보만 사용자가 확정한다. pooling(전략 상위 결과 합집합)은 쓰지 않는다 — 전략 결과를 먼저 보게 되고 pool에 든 전략이 유리해진다. 놓침 비율은 음성 표본 감사로 보고한다
- 등급 규칙 G1~G7 · 질의 채택 규칙 Q1~Q5는 확정 시트에

**변경 (2026-10-12, 사용자 결정 — 전략 결과 0건): 놓침 감사를 판정 잔여 풀링으로** — 위 「pooling은 쓰지 않는다」는 **기본 정답 집합**에 대해 그대로다(전수 스크리닝). 바뀌는 것은 놓침 감사: 무작위 음성 표본 대신, 등록된 전략 전부를 돌린 뒤 어느 전략이든 문서 단위 상위 10에 올렸는데 판정이 없는 문서만 **전략을 가리고** 판정해 gold@v1.1로 보탠다(v1 점수도 같이 보고). 전략마다 judged@10을 낸다. 전략을 전원 넣고(pool에 든 전략이 유리해지는 문제) 판정자에게 전략을 가린다(결과를 먼저 보는 문제). 판정자 자기일관성 감사는 뺀다 — 사람 표본 61장이 이미 쟀다. 절차 전문: 확정 시트 §4 「스크리닝 감사 재구성」

### 표본 크기의 한계

유형별 질의가 15\~20개면 유형별 결론은 **방향성**까지만 말한다. 유형별로 "유의하게 이긴다"를 말하려면 더 많이 필요하다 — 첫 실행의 분산을 보고 정한다(확정 시트 §10과 같은 원칙). 케이스가 실제 사례 몇 개의 변형이면 독립 표본이 아니다(CLAUDE.md 규율 5).

## 5. 지표


| 층          | 지표                                                                                                                                        | 도구       |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| 표준 IR      | Recall@5·10·20 · nDCG@10 · MRR                                                                                                            | `ranx`   |
| JHS 전용     | **Correct Component@k** · **Correct Version@k** · **Correct Source Type@k** · **Impact FP rate** (틀린 component를 영향 있다고 올린 비율, 제안서 Risk 4) | 자체       |
| 시스템        | p50·p95 지연 · 색인 구축 시간 · 색인 크기 · 메모리 · **구축 LLM 비용($)**                                                                                    | 자체 계측    |
| end-to-end | 이 검색을 쓴 판정이 공용 eval을 통과하는가 (revisit·detect·capture)                                                                                       | M9 공용 채점 |


**변경 (2026-10-13, HYO-34 — JHS 지표 정의 확정, 사용자 결정)** — 위 표는 지우지 않는다. **test 결과 0건 · dev nDCG는 본 뒤에** 정했다(dev 조정 `eval/arena/dev-tuning-2026-10-13.md`). 정의를 이 커밋으로 먼저 등록하고, dev 재채점은 그 뒤에 한다.

- **전부 보조 지표다.** 30칸 적중 판정은 §7-1대로 nDCG@10만 쓴다. 유형별 표본이 작아(dev 3~4 · test 4~8) 비율을 내지 않고 **질의별 사례 표**로만 내는 것이 있다. k는 문서 단위 10(헤드라인 nDCG@10과 같다)
- **Correct Version@k (C·E)** — 상위 k에 정답 릴리스가 있나. 정답 릴리스 = 그 질의 qrels 등급 2인 `github-release:` 문서 중 tag의 버전이 `expected_version`과 같은 것(기계적으로 뽑는다). C는 등급 2가 이것 하나뿐이라 Recall@k와 같다 — 그렇게 적는다
- **버전 혼동 사례 표 (C만)** — 시트 §5의 Correct Version@k가 C에서 Recall과 같아 따로 둔다. JHS의 실제 실패는 「같은 패키지의 다른 버전」이다
  - 형제 = 정답 릴리스와 같은 repo · 같은 패키지(tag의 `<패키지>==` 접두어 — 모노레포 `langchain-ai/langchain`은 패키지가 여럿이다)의 다른 버전 릴리스 중 **그 질의 qrels 등급 0이거나 판정 없음**. 등급 1 이상인 형제는 판정자가 쓸모 있다고 본 문서라 혼동이 아니다
  - 형제를 정답보다 **이전/이후 버전**으로 나눠 적는다. **위험 = 이전 형제가 정답보다 위에 있다 · 또는 정답이 상위 k에 없는데 이전 형제가 상위 k에 있다.** 이후 형제는 적되 위험으로 치지 않는다 — 릴리스 노트는 그 버전의 변경분만 적어 이후 버전 노트는 근거가 없는 문서이고, 그 노트로 잘못 답해도 버전 고정(`>=`)이 보수적으로 틀린다(깨지지 않는다). 이전 버전으로 잘못 답하면 기능이 없는 버전에 고정해 깨진다. 이후 버전에서의 삭제·기본값 변경은 예외라 사례 표에서 사람이 본다
  - 형제가 없는 질의는 「형제 없음」. E는 넣지 않는다 — 지금 버전과 목표 버전 사이 릴리스가 전부 관련 문서다(dev E12: 형제 7개가 전부 등급 1)
- **Correct Component@k → 「component 근거」 사례 표 (E만)** — 원래 정의(상위 k 문서의 노드 ∩ 질의 노드)는 문서마다 노드 라벨이 있어야 하는데 없다. 문서 단위로 「같은 repo의 스택 문서」를 세면 component가 아니라 repo를 맞힌 것이다(스택 절 하나에 component가 다 있다). 그래서 **청크 단위**로 내린다: 상위 k 문서의 대표 청크(문서마다 최고 순위 청크, §4)가 같은 repo의 C-CODE 청크이고 (a) 스택 절의 **한 줄(표 행)**에 질의 기술의 별칭과 질의 component가 함께 있거나 (b) manifest 청크인데 manifest 경로의 디렉터리 이름이 질의 component이고 청크에 기술 별칭이 있으면 근거다. 별칭은 `nodes@v1`(아래). manifest가 이미 등급 2인 질의는 「Recall과 겹침」으로 표시한다. - **알려진 한계 (고치지 않음)** — component 근거의 stack-row는 별칭을 대소문자 무시로 찾아, 패키지 별칭(`openai` · `anthropic`)이 「외부 모델·서비스」 표의 회사 이름(「OpenAI `gpt-6-sol` …」) 행에도 걸린다. 표 종류나 노드 종류로 가르면 「Claude Code routines」 같은 정당한 행을 놓치는 규칙이 되어 두지 않는다. 사례 표에 근거 청크가 함께 적히므로 사람이 볼 때 거른다

**Full Context는 IR 지표로 재지 않는다.** 전부 넣으니 Recall이 늘 1이다. Full Context는 **end-to-end 통과율 · 토큰 비용 · 지연 · 컨텍스트 한도**로만 재고, 그 축에서 다른 전략과 만난다. "어느 규모에서 무너지는가"는 이 축에서 나온다.

### 7-1. 예측 격자 (필수, 가벼움)

s7 구조 그래프 : 이미 온톨로지에 버전별 관리가 다 되어 있을 거 같은데 구조로 못 찾는 것도 말이 안되는 거 같고 → **결정(2026-09-29): S7 그래프 스키마에 버전 노드(Release)와 manifest의 버전 고정(`fastapi>=0.110` 등) 관계를 넣는다.** 그래서 E와 함께 C도 중→상 (C는 버전 질의 자체라 앞뒤를 맞춤)

## 9. 결과 저장 — 나중에 추가해도 비교되게

실행 하나 = `(전략 ID, 전략 버전, 코퍼스 버전, gold 버전, 티어, 시드)` 키로 결과를 쌓는다.

```
arena/results/
  S4.v1__C-ADR@v1__gold@v1__T0__seed0/
    run.json        # 질의별 순위 목록 (ranx run 형식)
    metrics.json    # 지표
    system.json     # 지연·구축 시간·색인 크기·메모리·비용
    env.json        # 기기(M1/4070)·장치(mps/cpu/cuda)·라이브러리 버전·커밋 해시
```

- 새 전략(예: 나중의 온톨로지)은 같은 코퍼스·gold 버전으로 돌리면 **옛 결과와 바로 짝지어 비교**된다
- 코퍼스나 gold가 바뀌면 옛 결과는 그 버전의 기록으로 남고, 새 버전에서 전부 다시 돈다
- 색인 결과물은 git에 넣지 않는다. `results/`의 json은 넣는다 — 작고, 비교의 증거다
- `env.json`의 기기 기록: 4070에서 만든 색인과 M1에서 만든 색인이 같은 결과를 내는지 한 번 확인한다(M1 기준 원칙)
