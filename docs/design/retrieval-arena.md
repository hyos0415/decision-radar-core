# Retrieval Arena 설계

> 초안 v0 · 2026-09-29 · 상위 문서: `overview.md` (M3, G1·G2)
> **가설 칸은 비어 있다** — 사용자가 사전 등록한다. 이 문서는 틀(무엇을, 무엇으로, 어떻게 공정하게)만 정한다.

## 1. 질문

> **이 태스크(기술 결정 기록의 발견·영향 매칭·재검토)에 최적인 검색 방법은 무엇인가 — 질의 유형별로, 규모별로.**

단일 승자를 고르는 게 목표가 아니다 (제안서 §12: "Exact → BM25, Impact → Hybrid + Internal Context" 같은 결과가 나오면 라우터로 간다).
세 가지를 답한다:

1. 질의 유형(A~K)마다 어느 전략이 이기는가 → 라우터 설계의 입력
2. 규모가 커질 때 **Full Context(= 스킬 방식)가 어디서 무너지고**, 그때 무엇으로 넘어가는가 (G1)
3. 이기는 전략의 **구축 비용**(시간·크기·LLM 비용)이 그 이득만큼의 값을 하는가 (retrieval-arena 판정의 남은 틈 c)

## 2. 코퍼스

| ID | 코퍼스 | 내용 | 언어 | 단위(청크) |
|---|---|---|---|---|
| **C-ADR** | 결정 기록 | 실제 ADR(`docs/adr/*.md`) — frontmatter + 본문 | 한국어 위주 | **파일 단위** (2026-09-29 결정) |
| **C-DOC** | 외부 문서 | 릴리스 노트·공식 문서·가격표·모델 카드·issue — **버전·날짜·source_type 메타데이터 필수** | 영어 위주 | **헤딩 기준** (2026-09-29 결정) · 길이 상한 미정 |
| **C-CODE** | 대상 repo | CLAUDE.md 스택 절·manifest·코드(import 관계) | 혼합 | **함수 단위** (2026-09-29 결정) · 함수가 없는 파일(CLAUDE.md·manifest) 처리 미정 |

- 커뮤니티 신호(trend-radar)는 **코퍼스가 아니다** — 후보를 올리는 입구일 뿐, 검색 결과로 근거가 되지 않는다(R2)
- **청크 방식은 교란 변수다.** 코퍼스마다 한 가지로 고정하고, 모든 전략이 같은 청크를 받는다(그래프 전략은 청크 대신 노드). 청크 방식을 바꾸면 코퍼스 버전이 바뀐다
- 청크 방식은 사용자가 사전 등록 때 정한다 (§6)

### 버전과 규모 티어

코퍼스는 `C-ADR@v1`처럼 버전을 붙여 동결한다. 버전이 바뀌면 모든 전략을 다시 돌린다(비LLM 전략은 재실행 비용이 거의 0).

| 티어 | C-ADR | C-DOC | 목적 |
|---|---|---|---|
| T0 | 실제 ADR 전부 (수~수십 건) | 실제 대상 기술 문서 | 실사용 규모 |
| T1 | 50 | ×10 | |
| T2 | 500 | ×100 | Full Context가 버거워지는 구간 후보 |
| T3 | (선택) Full Context가 불가능한 규모 | | 컨텍스트 한도 밖 |

- T1 이상의 ADR은 **합성**이다. 실제 기술 목록에서 결정을 늘려 만들되, 합성 ADR의 gold 정답은 합성 규칙에서 나오므로 **실제 ADR 질의와 따로 집계**한다
- 합성은 평가 대상 모델과 다른 회사 모델로 만든다 — 같은 모델이 만들고 검색하면 표현이 겹쳐 유리해진다

## 3. 질의 유형

제안서 §11의 A~J에 **K를 추가**한다.

| 유형 | 질의 예 | 어느 흐름에서 생기나 |
|---|---|---|
| A 정확 조회 | "vLLM의 `max_num_seqs` 기본값이 바뀐 버전은?" | revisit(web·version) |
| B 의미 검색 | "벡터 색인 저장 공간을 줄이는 기술은?" | detect |
| C 버전·시간 | "LEANN이 incremental insert를 지원하기 시작한 릴리스는?" | revisit |
| D 대안 탐색 | "regex PII 마스킹을 대체할 기존 기술은?" | detect·capture |
| E 호환성 | "새 FastAPI 릴리스가 우리 스택과 호환되나?" | detect |
| F 외부 → 내부 영향 | "이 vLLM 변경이 어느 repo·component에 닿나?" | detect (**틈 ④**) |
| G 커뮤니티 실패 | "공식 문서엔 없지만 사용자들이 겪는 문제는?" | (신호만 — 근거 아님) |
| H 대체·보완 | "이 기술은 현재 구현을 대체하나 보완하나?" | detect·capture |
| I 모델 전환 | "새 모델로 바꿀 가치가 있나?" | (Could) |
| J 재검토 | "과거 기각 조건이 지금도 유효한가?" | revisit |
| **K 동일 결정 찾기** | "'Amazon Bedrock Guardrails / PII 마스킹'에 대한 기존 결정이 있나?" | capture·detect의 R7·R14 (**틈 ③**) |

K는 지금 `jhs.py match`가 문자열 일치로 하는 일이다. 규모에서 무너질 1순위 후보라서 따로 뺐다.

## 4. gold set

- **gold set을 만들기 전에 `eval-precondition` 모드 1로 전제를 확정한다** — 기존 eval(`eval/precondition-sheet.md`)과 같은 절차. 특히 "정답이 유일한가"(CLAUDE.md 규율 2: F1 가격 페이지 모호함)
- 판정 단계: 관련(2) / 부분 관련(1) / 무관(0). nDCG를 쓰려면 등급이 필요하다
- 초안은 LLM(평가 대상과 다른 회사)이 만들고 **사람이 확정**한다. 확정은 사용자가 한다 — 정답을 정하는 쪽이 전략을 짜는 쪽과 같다는 점은 한계로 기록한다
- 분할: **dev**(전략 튜닝용, 들여다봐도 됨) / **test**(봉인 — 사전 등록된 최종 비교에서만 연다)
- 버전: `gold@v1`. 질의를 추가하면 버전이 바뀐다. test에 질의를 보탤 때는 새 전략을 본 뒤가 아니라 **등록 시점 전에**

### 표본 크기의 한계

유형별 질의가 15~20개면 유형별 결론은 **방향성**까지만 말한다. 유형별로 "유의하게 이긴다"를 말하려면 더 많이 필요하다 — 첫 실행의 분산을 보고 정한다(확정 시트 §10과 같은 원칙). 케이스가 실제 사례 몇 개의 변형이면 독립 표본이 아니다(CLAUDE.md 규율 5).

## 5. 지표

| 층 | 지표 | 도구 |
|---|---|---|
| 표준 IR | Recall@5·10·20 · nDCG@10 · MRR | `ranx` |
| JHS 전용 | **Correct Component@k** · **Correct Version@k** · **Correct Source Type@k** · **Impact FP rate** (틀린 component를 영향 있다고 올린 비율, 제안서 Risk 4) | 자체 |
| 시스템 | p50·p95 지연 · 색인 구축 시간 · 색인 크기 · 메모리 · **구축 LLM 비용($)** | 자체 계측 |
| end-to-end | 이 검색을 쓴 판정이 공용 eval을 통과하는가 (revisit·detect·capture) | M9 공용 채점 |

**Full Context는 IR 지표로 재지 않는다.** 전부 넣으니 Recall이 늘 1이다. Full Context는 **end-to-end 통과율 · 토큰 비용 · 지연 · 컨텍스트 한도**로만 재고, 그 축에서 다른 전략과 만난다. "어느 규모에서 무너지는가"는 이 축에서 나온다.

규칙:
1. **기준선(S0·S1·S2)은 가설이 없어도 반드시 돈다** — 직접 고른 전략이 "무엇보다" 나은지 잴 기준
2. **틀릴 수 있게 쓴다** — "좋을 것" 말고 "F 유형에서 S5보다 Correct Component@5가 높다"

## 8. 공정성 규칙

| 규칙 | 이유 |
|---|---|
| 모든 전략이 같은 코퍼스 버전·같은 청크·같은 gold 버전 | 데이터 차이가 전략 차이로 둔갑하지 않게 |
| 전략마다 엔진 하나로 고정 (BM25 = ES) | 엔진 비교는 범위 밖 (retrieval-arena 판정 DROP) |
| 튜닝은 dev에서만, 보고는 test | test 과적합 방지 |
| 같은 질의로 짝지어 비교(paired) + 비교 횟수만큼 유의 기준 보정 | 전략이 늘수록 운으로 이기는 전략이 생긴다 (`study-notes.md`) |
| LLM이 끼는 전략(S9·S10)은 시드·반복 ≥3 | 실행마다 결과가 흔들린다 (kb-arena `variance` 규칙 차용) |
| 비교 모드의 end-to-end는 스킬과 같은 Claude 모델 | `overview.md` §7 |

## 9. 결과 저장 — 나중에 추가해도 비교되게

실행 하나 = `(전략 ID, 전략 버전, 코퍼스 버전, gold 버전, 티어, 시드)` 키로 결과를 쌓는다.

```
arena/results/
  S4.v1__C-ADR@v1__gold@v1__T0__seed0/
    run.json        # 질의별 순위 목록 (ranx run 형식)
    metrics.json    # 지표
    system.json     # 지연·구축 시간·색인 크기·메모리·비용
    env.json        # 기기(M1/4070)·장치(mps/cpu/cuda)·라이브러리 버전·커밋 해시
```

- 새 전략(예: 나중의 온톨로지)은 같은 코퍼스·gold 버전으로 돌리면 **옛 결과와 바로 짝지어 비교**된다
- 코퍼스나 gold가 바뀌면 옛 결과는 그 버전의 기록으로 남고, 새 버전에서 전부 다시 돈다
- 색인 결과물은 git에 넣지 않는다. `results/`의 json은 넣는다 — 작고, 비교의 증거다
- `env.json`의 기기 기록: 4070에서 만든 색인과 M1에서 만든 색인이 같은 결과를 내는지 한 번 확인한다(M1 기준 원칙)
