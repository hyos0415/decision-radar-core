# 합집합 파이프라인 — 스킬 라이브 검색을 수집 깔때기에 합치기

> 2026-11-03 · HYO-167 · 상태: **설계 중** — 실사용 기간(~2026-11-22)에는 켜지 않는다 (`comparison-protocol.md` §9 「두 도구를 같이 켜기」)
> 관련: 같은 주 재생 HYO-164 · 같은 순간 짝(스킬 그림자) HYO-166 · 판정 HYO-57

## 1. 왜

스킬(실행할 때 웹을 찾는다)과 제품(매주 정해진 출처를 모아 얼리고 거른다)은 같은 일을 하는 **다른 체계**다. 굴려 보니 잡는 것이 달랐다.

| 사례 | 스킬 | 수집 파이프라인 | 갈린 곳 |
|---|---|---|---|
| Langfuse Python SDK v5.0.0 (ADR 0015) | 업그레이드 가이드로 찾음 | GitHub 태그만 있고 release 객체가 없어 releases API에 안 보임 — v5.0.1은 W43에 들어왔으나 상한에서 잘림 | 출처 구멍 · 상한 |
| Anthropic Python SDK v2.0.0 (ADR 0016) | 10/26 실행 때 찾음 | 다음 날 W44 코퍼스에 들어옴 · 관문 통과 · 상한(Electron 5칸)에서 잘림 | 수집 시점 · 상한(HYO-147로 고침) |

그래서 가설(사용자 11/3): **취사선택이 아니라 함께 돌려 범위를 넓히는 것이 낫다.** 아직 근거는 두 건이다. 값어치는 재생(HYO-164, W41~W43)과 같은 순간 짝(HYO-166, 11/10 · 11/17)이 잰다. 한쪽만 잡은 항목이 거의 없으면 합치지 않는다 — 판단은 11/23.

## 2. 정한 것 (사용자 결정 2026-11-03)

| | 결정 | 이유 |
|---|---|---|
| D1 실행 시점 | 스킬 검색은 **수집과 같은 주기·같은 순간** (아래 §5에서 위치 확정) | 시점 차이를 없애야 갈린 이유가 체계 차이로만 남는다. 그림자 실행과 같은 자리라 그대로 이어진다 |
| D2 재현성 | **스킬은 URL을 찾고, 원문은 수집기가 받아 얼린다** | 스킬의 넓이(어디를 볼지)와 파이프라인의 기록(재현 · 버린 이유)을 합친다. WebFetch는 작은 모델의 요약만 주므로 원문은 따로 받아야 한다 |
| D3 범위 | **detect 먼저**, revisit은 나중 | 갈린 증거가 모두 detect 쪽이다. revisit은 얼린 출처(HYO-159)가 1주라 자료가 없다 |
| D5 실행 위치 | **수집 PC(Windows) 주간 사슬의 한 단계** — 관문 다음 `skill` 단계, 합친 detect 입력을 함께 push (§5 가) | 스킬과 코퍼스가 같은 시각의 세상을 본다 · 한 기기에서만 얼린다 |
| D4 표시 (기본값) | 항목마다 **찾은 체계**(`found_by`: 수집 · 스킬 · 둘 다) | 합친 뒤에도 각자의 몫을 매주 잰다 — 상호 감사가 운영 중에도 이어진다 |

## 3. 그림

```
화 16:00  수집 ─▶ 얼림(corpus@W) ─▶ 등급 ─▶ 관문 ─┐
                                                   ├─▶ 합치기·중복 제거 ─▶ 상한 ─▶ detect 입력 ─▶ 모델 ─▶ 초안
          스킬 detect(라이브 웹) ─▶ URL·패키지·버전 ─▶ 수집기가 원문 받기 ─▶ 얼림 ─┘
                                                                  (found_by 표시)
```
합류 지점(관문 앞인지 뒤인지)은 아직 안 정했다 — §6 E1.

## 4. 구성 요소

- **스킬 줄**: `skill@v1` detect를 스킬만 복사한 빈 실행 루트 + ADR 사본에서 돌린다 — 그림자(HYO-166)와 **같은 실행기**를 쓴다. PR · issue는 막는다
- **후보 뽑기**: 스킬 초안의 근거 링크 + 패키지 · 버전. transcript에서 연 URL(WebSearch · WebFetch)까지 넣을지는 §6 E5. 그림자도 같은 함수로 뽑는다 — 그래야 그림자 결과가 곧 「합쳤다면」의 자료가 된다
- **원문 받기 · 얼리기**: 수집기의 받기 코드로 URL 원문을 받아 `radar-snapshots/detect/<주>/skill/`에 둔다 (`items/S01.md` · `fetched_at` · 상태). 못 받으면(비공개 페이지 등) 이유를 남기고 스킬이 쓴 요약은 쓰지 않는다
- **정규화**: detect 입력과 같은 모양(`id` · `title` · `kind` · `package` · `version` · `summary` · `url` · `source_type`). `id`는 `skill:<정규화 URL>`
- **합치기 · 중복 제거**: 같은 항목 = 정규화 패키지 이름 + 릴리스 주 버전, 패키지가 없으면 정규화 URL (재생 · 그림자와 같은 기준). 겹치면 수집 쪽 항목을 남기고 `found_by`에 둘 다
- **기록**: `funnel.json`에 스킬 줄 건수(찾음 · 받음 · 못 받음 · 겹침 · 스킬만)를 더한다. 실행 요약 한 줄에도

**구현 상태 (2026-11-04, 꺼진 채 — `RADAR_UNION=on`일 때만)**
- 스킬 줄 · 후보 뽑기 · 같은 항목 키: `pipeline/skill_line.py` — 그림자(HYO-166, `desktop/backend/service.py`)와 **같은 함수**. 스킬은 `skill@v1` tag에서 꺼낸다
- 원문 받기 · 얼리기 · 정규화 · 합치기 · `found_by`: `pipeline/union.py` (`run` · `replay`). GitHub 릴리스 태그 주소는 releases API 본문을 먼저 받고, release 객체가 없으면(Langfuse v5.0.0) 태그 페이지로
- 패키지 이름: 근거 링크의 GitHub 저장소 → 코퍼스의 의존성(meta.repo → meta.dependency) · pypi/npm 주소 · 기술 이름이 아는 의존성 낱말을 다 품음(「Anthropic Python SDK」 → anthropic). 주 버전은 1 이상이면 첫 자리, 0.x면 `0.<둘째>`
- **아직 안 한 것**: 합류(E1)와 몫(E2)에 따라 달라지는 부분 — 주간 사슬 단계 자리 · 관문/상한에 붙이기 · `funnel.json` 칸. `union.merged_items()`(가) · `union.skill_only()`(나)가 붙일 자리다
- 재생 데이터 배관 확인(원문 받기 포함, 판정 없음): 스킬 기간 초안 ADR 0015 · 0016 × 얼린 W43 · W44 — W43에서 Langfuse v5.0.0 = 수집과 겹침(v5.0.1 · v5.0.2) · Anthropic v2.0.0 = 스킬만, W44에서 둘 다 겹침. 「갈린 단계」 분석은 재생(HYO-164) 몫

## 5. 어디서 도나 — D1을 어떻게 구현하나 (사용자 결정 2026-11-03: **가**)

| 안 | 흐름 | 좋은 점 | 걸리는 점 |
|---|---|---|---|
| **가. 수집 PC 사슬의 한 단계 (채택)** | 화 16:00 Windows 사슬: 관문 다음에 `skill` 단계 → 원문 받기 · 얼리기 → 합친 detect 입력 push → 맥 18:00 detect가 읽는다 | 스킬과 코퍼스가 같은 시각의 세상을 본다(둘 다 ~16:00). 「한 기기에서만 얼린다」 규칙(CLAUDE.md)을 지킨다. 맥 detect는 그대로 | 스킬 실행이 detect보다 1.5시간 이르다. Windows에도 `claude` 로그인이 필요(있음) |
| 나. 맥 detect 직전 | 맥 18:00: 스킬 → 원문 받기 → 얼리기 → 합치기 → 제품 detect | 말 그대로 detect와 같은 순간 | 맥이 radar-snapshots에 push — 두 기기가 같은 폴더를 얼린다. 맥이 덮여 있으면(11/3처럼) 스킬도 밀린다 |

11/3 결정의 뜻은 「시점 차이를 없앤다」였다. 가는 그 기준을 detect가 아니라 **코퍼스**에 맞춘다 — 비교할 상대가 코퍼스이므로 이쪽이 더 정확하다. 그림자(HYO-166)는 등록대로 맥 detect 직후에 돈다(기록만 · push 없음 — 이 문제가 없다).

## 6. 열린 결정

| | 무엇 | 언제 정하나 |
|---|---|---|
| E1 | 합류 지점 — 가. 출처 하나로 관문 앞 · 나. 관문 뒤 별도 줄(스킬이 이미 관련성을 판단) · 다. 끝에서 초안끼리. **조건 (사용자 2026-11-04)**: 합집합 뒤에는 스킬로 따로 역수입하지 않는다 — 그러려면 스킬이 찾은 항목도 **자리 질의 · 질의별 top-k의 후보**로 들어가야 한다. 가면 자연히 된다(코퍼스 항목과 같은 길). 나 · 다를 고르면 「자리 질의는 합친 뒤 후보 전체에 돌린다」를 조건으로 단다 | 재생 결과 뒤 — 스킬만 잡은 항목이 관문에서 떨어지는지 본다 |
| E2 | 상한 — 공유 5칸 vs 스킬만 잡은 항목에 자리 예약 | 재생 · 그림자 뒤 — 한쪽만 잡은 건수를 본다 |
| ~~E3~~ | 실행 위치 — **가. 수집 PC 사슬의 한 단계** (사용자 2026-11-03) | 정함 |
| E4 | 비용 — Max 종료(11/22) 뒤 주당 `claude -p` +1을 어느 요금제로 | 11/22 전 |
| E5 | transcript에서 연 URL도 후보로 넣나 (넓이 ↑ · 소음 ↑) | 그림자 transcript를 본 뒤(봉인 해제 11/22) |

## 7. 안 하는 것 · 위험

- 실사용 기간(~11/22)에 켜지 않는다. 구현은 꺼진 상태(설정 플래그)로 머지하고, 재생 데이터로만 시험한다
- 스킬의 웹 검색은 다시 돌릴 수 없다 — 같은 주를 재현하는 것은 **얼린 원문**이지 검색이 아니다. 「스킬이 무엇을 찾았나」는 그 주 기록으로만 남는다
- 스킬만 잡은 항목이 거의 없으면 합치지 않는다 — 세션 비용만 는다 (11/23 판단)
