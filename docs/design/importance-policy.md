# 중요도 정책 `importance-policy@v1`

> **등록 — 2026-09-30, 결과 0건 시점.** 등록 커밋이 증거다. 이후 바꾸면 원래 내용을 지우지 않고 `변경 (날짜, 이유)`로 남기거나 v2로 새로 등록한다 (CLAUDE.md 규율 7).
> 초안은 Claude가 채웠고, 사용자가 검토해 기준선·등급을 그대로 받아들였다. 사용자 결정: 두 등급 동시 적용 · 모델 분류 + 스크립트 검증 · 헤드라인 = 소음 비율 · 영향 범위·대체 난이도 v1 제외 · 주당 5개 표시(`5/N`).

## 1. 왜 필요한가

detect(`docs/design/overview.md` §4 틈 ④의 제품 버전)는 다음 순서로 돈다.

```
C-CODE(repo 전체) → 기술 단위 추출 → [중요도 필터] → 질의 생성 → C-DOC 검색 → C-ADR 검색(K: 이미 결정했나) → 초안 / 건너뜀(R14)
```

repo 전체에서 기술을 뽑으면 수십 개가 나온다(pydantic·requests·dotenv…). 거르지 않으면 소음에 묻힌다.
지금 있는 필터는 명세 A5(`docs/spec-work-order.md` A부)의 **변화 종류** 필터 하나다(breaking·deprecation·security·yanked·major만). 이 필터는 **기술이 얼마나 무거운지는 모른다.**

**중요도 = 기술의 무게(축 1) × 일어난 변화의 종류(축 2)**

원칙:
- 축 1은 **manifest·Dockerfile·import에서 결정론적으로 계산**한다. 모델에게 판단을 맡기지 않는다 (CLAUDE.md 규율 1)
- 스크립트로 계산되는 부분은 스킬에도 넣는다 (규율 8 역수입). 제품만의 몫은 코드를 읽어야만 아는 부분이다

## 2. 축 1 — 기술 등급

### 2-1. 등급 (세분화 후보)

| 등급 | 이름 | 무엇 | 예 (실제 repo) | 확정 |
|---|---|---|---|---|
| L0 | 언어 런타임 | 인터프리터·언어 버전 | Python 3.12 | 확정 |
| L1 | 실행 기반 | 베이스 이미지 · 서빙 엔진 · GPU 스택 | `python:3.12-slim` · `vllm/vllm-openai` · llama.cpp `llama-server` · CUDA | 확정 |
| L2 | 호스팅 모델 (v1.1: 호스팅·로컬) | 외부 API로 부르는 모델 (v1.1: 로컬 서빙 모델 포함) | Bedrock `nova-pro`(운영 기본) · `claude-sonnet-5` · `gpt-5.6-terra` · Jev | 확정 |
| L3 | 호스팅 서비스 | 모델이 아닌 외부 서비스·공공 API (v1.3: 남이 운영하는 것만) | Langfuse Cloud · Bedrock Guardrails · Finlife API · 국가법령정보 API | 확정 |
| L4 | 앱 프레임워크 | 앱의 뼈대 — 바꾸면 코드 전반이 바뀜 | fastapi · pydantic · uvicorn · jinja2 | 확정 |
| L5 | 공급자 SDK | L2·L3을 부르는 클라이언트 (v1.2: L1·L2·L3) | boto3 · anthropic · openai · google-genai · langfuse · typesafe-sdk | 확정 |
| L6 | 도메인 라이브러리 | 특정 기능 하나를 맡음 | kiwipiepy · pdfplumber · torch·transformers | 확정 |
| L7 | 개발·테스트 도구 | 운영에 안 들어감 | pytest · ruff · k6 | 확정 |
| L8 | 유틸 | 작고 대체 쉬움 | python-dotenv · tzdata · requests · httpx | 확정 |

**L2(호스팅 모델)를 따로 뺀 이유**: 모델은 우리가 버전을 고정해도 **제공자가 은퇴(retire)시키면 끝**이다. 라이브러리와 달리 "올리지 않으면 안전"이 성립하지 않는다.

### 2-2. 보정 축 — 등급을 올리거나 내린다

| 보정 | 값 | 효과 | 확정 |
|---|---|---|---|
| **경로** | 운영(Dockerfile 설치·api·운영 기본값) / 개발(eval·scripts·비교용) | 개발 전용이면 → 보안만 남김 | 확정 |
| **영향 범위** | 쓰는 component 수 · import 위치 수 | **v1 제외** — 등급을 올리면 후보가 늘어 소음 우선 원칙과 반대. 값은 기록만 한다 (v2 판단 자료) | 확정 |
| **고정 방식** | 떠 있음(`latest`) / 범위(`>=`) / 고정(`==`·lock) | 떠 있으면 → 새 minor도 남김 (자동으로 들어오니까) | 확정 |
| **데이터 민감도** | PII·환자 데이터가 지나는 경로인가 | 지나면 → 보안·deprecation 무조건 남김 | 확정 |
| **대체 난이도** | 바꾸려면 몇 파일을 고쳐야 하나 | **v1 제외** — import 위치 수로 계산하면 영향 범위와 같은 값이 된다 | 확정 |

## 3. 축 2 — 변화 종류

| 변화 | 뜻 | 출처 예 |
|---|---|---|
| breaking | 우리 코드가 깨질 수 있는 변경 | 릴리스 노트 "Breaking changes" |
| deprecation | 곧 없어질 예정 | deprecation 공지 |
| **우리 버전 EOL** | **우리가 쓰는 버전**의 지원 종료 | Python 3.12 EOL 일정 |
| security | 보안 패치·CVE | GitHub Security Advisory |
| yanked | 배포 철회 | PyPI yanked |
| major | 메이저 버전 | semver |
| minor·patch | 그 외 | — |
| **모델 은퇴** | 호스팅 모델의 retirement·deprecation 일정 | 제공자 모델 문서 |
| **가격·한도 변경** | 호스팅 서비스의 가격·rate limit | 가격표 |
| **후속 모델** (2026-10-16 추가, 아래 변경) | 우리가 쓰는 L2 모델과 같은 계열의 더 높은 버전이 나왔다 — 스크립트가 제목으로 판정 | 제공자 출시 공지 · HN |

"새 버전이 나왔다"(예: Python 3.14 출시)는 대부분 소음이다. 무거운 기술일수록 **우리 버전에 무슨 일이 생겼나**를 본다.

**변경 (2026-10-16, 사용자 — HYO-130)**: breaking에 「표시가 없어도 **기존 함수·엔드포인트가 다른 값을 돌려주거나 다른 인자를 받는다고 적힌 변경**, **저장 포맷 버전 올림**」을 넣는다. 타입 표기·스키마를 바로잡는 수정은 넣지 않는다. 계기: llama.cpp v0.6.0(`mtmd_get_memory_usage()` now returns a struct · 세션 포맷 버전 올림)을 네 측정의 모델들이 거의 늘 breaking으로 봤고, 정답(표시·안내 없으면 아님 — 정답지 D3)이 의심스러웠다(규율 2). 분류 프롬프트의 정의도 같은 문구로 고쳤다

**변경 (2026-10-16, 사용자 — HYO-129, 결과 0건)**: 변화 종류 **후속 모델**(`successor_model`)을 더한다. 계기: 「같은 가격에 4.5 쓸래 5.5 쓸래? 하면 당연히 5.5」(사용자) — 우리가 쓰는 모델보다 나은 같은 계열 후속 모델 소식(예: Claude Haiku 5.5, HN 1047점)이 9개 종류 어디에도 안 맞아 늘 버려졌다. 은퇴와는 다르다 — 은퇴는 날짜부터 호출이 실패하는 **강제 이전**이고, 후속 모델은 지금 모델이 계속 도는 **선택 실험**이다(HYO-129 논의). ① **모델이 아니라 스크립트가 판정한다**(규율 1, `pipeline/importance/successor.py`): 기술 이름을 계열(숫자 아닌 토막)과 버전(숫자 토막, 6자리 이상 날짜 스냅숏은 뺀다)으로 나누고, 소식 제목에 같은 계열 + 더 높은 버전이 나오면 그 기술(등급에 L2가 있는 것만)에 후속 모델 행을 붙인다 — `claude-haiku-4-5-20251001`에 「Claude Haiku 5.5」, `gpt-6-luna`에 「GPT-6.1 Luna」. 같은 버전(「Claude Sonnet 5.5 now available on AWS」)·다른 계열(Haiku → Sonnet, 「Claude Fable 5」)은 아니다. 제목이 기술 이름을 직접 말하지 않아도 이 판정으로 소식이 그 기술에 걸린다 ② 모델에게 묻는 변화 종류(분류 프롬프트·스키마·Jev 질문)와 정답지의 변화 라벨은 **그대로**다 — 「새 모델 출시」 종류를 모델에 더하면 정답지·프롬프트·재측정이 다 따라와서다(사용자, 같은 날) ③ 한계: 버전이 이름에 없는 기술(Amazon Bedrock — 운영 모델 `nova-pro`는 usage 글 안에만 있다)은 보지 않는다 · 같은 계열의 변형(「GPT-7 Luna mini」)도 후속으로 잡는다 · 한 출시가 소식 여러 건(AWS 공지 · GovCloud 공지)으로 남을 수 있다(묶기는 HYO-127) · 관문은 레인 A만 본다 — HN·Reddit(레인 B)의 「Claude Haiku 5.5」(1047점)는 여기까지 오지 않고, 벤더 페이지 변경(`[anthropic] … 변경`)은 제목에 모델 이름이 없어 걸리지 않는다. 레인 A에서 걸리는 것은 벤더 피드 공지(「Claude Haiku 5.5 is now available on AWS」)다 ④ 남김 카드에 「강제 이전 / 선택 실험」 표시와 마감일을 붙이는 것은 따로 정한다(판정이 아니라 표시)
확인 (같은 날, API 없음): W41 정답지 102건 중 후속 모델로 걸리는 소식 0건 — 등록된 측정 결과(§8 C1~C3)는 바뀌지 않는다. 수집분 W41 2,290건 · W42 2,642건을 지금 스택 L2로 훑으면 걸리는 것은 GPT-6.1 Sol(W41 4건 · W42 2건)뿐이고, `gpt-6-sol`은 개발 경로라 버린다 — 지금 스택에서는 새로 남는 소식이 없다. **변경 (2026-10-27, 사용자 — HYO-147, 결정표·정렬 기준·5/N 표시는 그대로)**: 상한을 **기술당 1칸 먼저** 채운다. 위 정렬 순서대로 훑으며 기술마다 첫 후보만 고르고, 칸이 남으면 나머지를 같은 순서로 채운다(보이는 것도 잘린 것도 정렬 순서). 묶는 기술은 그 후보를 남긴 행 중 가장 높은 행(등급 → 심각도 → 기술 이름)의 기술이다. 이유: 2026-W44 관문 남김 31건 중 5칸이 전부 Electron이었다 — 같은 날 42·43·44·45 줄에 나온 **같은 보안 수정 한 묶음**(노트가 같다)과 45.0.0이 칸을 다 가져가, Anthropic API 2026-10-21·모델 은퇴 페이지 · OpenAI deprecations · langfuse security가 밀렸다. 정렬 키에 다양성이 없어서 생긴 일이다. 저장된 관문 결과에 다시 걸어 본 전/후(모델 호출 없음): W41 바뀐 칸 0 (4/4) · W42 1 (OpenAI changelog → anthropic SDK 1.12.0 deprecation) · W43 1 (claude-code v2.1.299 deprecation → Amazon Bedrock 가격 — 둘 다 L2, claude-code가 claude-sonnet-5-5 기술로 묶여서) · W44 4 (Electron 4건 → Anthropic 모델 은퇴 페이지 · OpenAI deprecations · Bedrock 가격 · langfuse security). 잘린 Electron 4건은 그대로 로그(`truncated`)에 남는다. 같은 W44가 드러낸 다른 틈 — 관문이 **우리 버전 숫자**를 몰라 "42.x 지원 종료"를 「우리 버전 EOL」로 붙였고 정작 우리 Electron 39가 지원 밖이라는 말은 없었다(§7 열린 문제) — 은 이 변경이 고치지 않는다 (HYO-148)

**변경 (2026-10-27, 사용자 — HYO-148, 결정표·보정 축·상한은 그대로)**: 판정 앞에 **범위 정리** 한 단계를 둔다 — 등급으로 행을 고르기 전에, 기술마다 「우리 버전 EOL」·「모델 은퇴」 라벨이 우리 버전·우리 모델인지 보고 아니면 그 기술의 라벨에서 뺀다(§3 변경 2026-10-27). 순서: 모델 라벨 → `normalize_changes`(프리릴리스 major · 덧붙인 minor_patch) → 범위 정리(기술마다) → 후속 모델 행 → 결정표·보정 축. 다 빠지면 그 기술은 minor·patch로 친다(「다른 줄의 EOL 공지」는 우리에게 그 정도다)

## 7. 열린 문제

- "놓친 것"은 사람이 따로 찾아야 잰다 — 4주 동안 무엇을 어떻게 찾아볼지 (예: 주 1회 대상 기술 릴리스 노트를 직접 훑기)
- 우리 버전 EOL은 manifest에 버전이 적혀 있어야 계산된다 — finance_verifier는 manifest가 없다
  → (2026-10-27, HYO-148) 관문이 manifest 버전을 읽어 다른 줄의 EOL을 뺀다(§3 변경). manifest가 없는 기술은 `override --set-version`(사람 입력). 아무 소식도 없을 때 우리 줄이 이미 지원 밖인지는 여전히 모른다 — 구조화된 지원 일정 출처는 새 이슈
- 호스팅 모델의 "운영 기본값 vs 비교용" 구분은 코드를 읽어야 안다 (medical-mate-ai `providers.py`의 기본 Extractor vs 가격표 항목) — 제품의 몫
