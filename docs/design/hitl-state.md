## 1. 무엇을 푸는가

제품에는 상태가 두 곳에 있다.

| 곳 | 무엇 | 누가 바꾸나 |
|---|---|---|
| **ADR repo (git 마크다운)** | 결정 기록 = state의 원본 (overview §3) | 제품, 그리고 **사람이 아무 때나** — 파일 직접 수정 · status 변경 · PR 머지 · revert |
| **LangGraph checkpoint (SQLite)** | 멈춘 그래프의 상태 — 승인 대기 초안, 실험 결과 대기 | 제품만 |

승인 대기·실험 대기는 며칠 걸린다. 그 사이 사람이 ADR repo를 바꾸면 checkpoint가 본 세상은 낡는다. **낡음은 예외가 아니라 평소다** — 승인해 두고 한동안 손대지 않는 일이 잦다 (사용자, 2026-10-06). 그래서 이 설계의 중심은 「재개할 때마다 세상이 바뀌었는지 확인하는 길」이다.

스킬에는 이 문제가 없다 — 매 실행이 새 세션이고 대기가 없다(overview §3). 이것은 **스킬 구조상 어려운 틈**(overview §4 오른쪽 열 「며칠 걸치는 흐름」)이라 제품이 증명할 곳이다. 역수입 대상이 아니다.

### 1-1. 지금 코드 (스파이크에서 옮긴 상태, `product/radar/capture.py`)

- `thread_id`가 `"capture"` **하나로 고정** — eval 케이스 하나씩은 되지만 대기 건이 여럿이면 서로 덮는다
- ADR 번호는 승인 뒤 쓸 때 정한다 (`propose_adr` → `radar.py next-id`)
- 재개할 때 **아무것도 다시 확인하지 않는다**
- 승인 뒤 초안이 validate에 걸리면 고칠 길이 없다 (스킬은 그 파일을 고친다 — E5 리뷰, 2026-10-06)
- 실험 단계 lifecycle(`EXPERIMENT_PROPOSED`~`RESULT_READY`)이 없다

### 기각한 안

| 결정 | 안 | 이유 |
|---|---|---|
| 1 | DB가 원본 | 사람이 git으로 ADR을 고치는 일이 막히거나 무시된다. 「결정 기록은 사용자 소유」(판정문 D)와 스킬·제품이 같은 데이터 위에서 도는 비교 전제가 깨진다 |
| 2 | ADR 프론트매터에 `lifecycle` 칸 | overview §2가 나눈 `status`(사람의 결정)와 lifecycle(파이프라인 진행)이 한 파일에 다시 섞인다. 진행할 때마다 결정 기록에 커밋이 쌓인다. 스킬과 같이 쓰는 schema의 의미가 기준선 기간에 바뀐다 (`radar.py validate`는 모르는 칸을 거부하지 않아 기술적으로는 들어가지만) |
| 2 | DB에만 | 결정 1과 부딪힌다 — DB를 지우면 실험 대기 중이었다는 사실이 사라진다 |
| 2 | 별도 파일 하나에 전부 | 동시에 쓰면 충돌, git 머지가 꼬인다 |
| 3 | (가) 거부하고 처음부터 재판정 | 사람이 이미 한 판단(승인)을 버린다. 낡음이 잦아서 매번 재판정이면 승인이 무의미해진다 |
| 3 | (나) 바뀐 부분만 조용히 재검사하고 계속 | 사람이 모르는 사이에 승인한 것과 다른 것이 저장될 수 있다 |
| 4 | 제안할 때 번호 예약 | `radar.py next-id`가 예약을 알아야 한다 → 스킬과 제품의 번호 규칙이 갈라진다. 대기 건끼리 번호가 겹치거나 빈 번호가 남는다 |
| 5 | 실행 하나 = thread | 초안 3개 중 하나만 대기해도 셋이 묶인다 |
| 5 | ADR 하나 = thread | ADR이 생기기 전 단계(`DISCOVERED`~`USER_REVIEW`)를 담지 못한다 |
| 5 | N일 뒤 자동 만료 | 낡음은 재개 검사(결정 3)가 잡는다. 만료는 사람의 승인을 말없이 버린다 → 대신 Inbox에 대기 일수를 보인다 |

## 3. 항목과 별도 파일

**항목(item)** = 파이프라인이 추적하는 한 건 (capture 대화 하나에서 나온 초안, detect 후보 하나, 실험 하나). `item-id`가 thread_id이자 별도 파일 이름이다.

### 3-1. 언제 파일이 생기나 — R9

명세 R9: capture는 **승인 전 파일 쓰기와 원격 부작용이 모두 0건**. 그래서 별도 파일은 **그 흐름이 ADR repo에 쓸 수 있게 된 첫 순간**에 생긴다.

| 흐름 | 별도 파일이 생기는 때 | 그 전 상태는 |
|---|---|---|
| capture | 사람이 승인한 순간 (write-ahead 의도와 같은 단계) | checkpoint에만 — 잃으면 대화를 다시 넣으면 된다 |
| detect | 초안 파일을 쓰는 순간 (detect는 원래 승인 없이 `proposed` 초안을 쓰고 PR로 검토받는다) | checkpoint에만 |
| 실험 | `EXPERIMENT_APPROVED` (사람의 승인) | checkpoint에만 |

이것은 결정 1의 귀결이기도 하다 — checkpoint에는 「아직 git에 없는 진행 중인 것」만 있다. 승인 전 단계는 잃어도 다시 만들 수 있는 제안이다.

### 3-2. 모양 (초안 — 필드는 구현하며 확정)

```yaml
id: 2026-10-06-capture-hanner-pii      # item-id = thread_id = 파일 이름
kind: capture                          # capture · detect · experiment
lifecycle: USER_REVIEW                 # overview §2의 단계
adr: null                              # ADR이 생기면 "0011"
created: 2026-10-06T11:40:00+09:00
updated: 2026-10-06T11:40:00+09:00
fingerprint:                           # 멈출 때 근거로 삼은 것 (§4) — 무엇을 넣을지는 §8 Q2
  adr_repo_commit: 9f1ca56
  files: {docs/adr/0004-leann-vector-index.md: 3a91c0de}
write_intent: null                     # §5. 쓰는 중이면 {adr, path, content_hash, state: intended|done}
history:                               # 지우지 않고 쌓는다
  - {at: 2026-10-06T11:40:00+09:00, to: USER_REVIEW, by: graph}
```

- `status` 칸은 없다 — status는 ADR 파일에 있고 사람만 바꾼다 (R8). 별도 파일이 status를 흉내 내지 않는다
- 사람이 손으로 고쳐도 된다 (git이 원본). 형식 검사는 제품이 읽을 때 한다 (§8 Q5)
- **고아**: 별도 파일의 `adr`가 가리키는 ADR이 없어졌거나(사람이 지움·번호 바꿈), ADR repo에 없는 thread가 checkpoint에 남았을 때. 결정 1에 따라 검사기는 **표시만 하고 자동으로 고치지 않는다**

## 4. 재개 프로토콜 (결정 3)

재개는 「사람이 답했다」(승인·거부) 또는 「기다리던 것이 왔다」(실험 결과)로 시작한다. 순서:

1. **별도 파일을 읽는다.** 없으면 (§3-1에 따라 아직 안 생긴 단계가 아닌데) → 고아 checkpoint. 멈추고 사람에게 보인다
2. **쓰다 만 것부터 정리한다** — `write_intent`가 `intended`면 §5의 회복을 먼저 한다
3. **지문을 다시 계산해 멈출 때의 것과 비교한다**
   - 같으면 → 그대로 재개
   - 다르면 → **무엇이 바뀌었는지** 요약해 다시 interrupt: 바뀐 ADR 파일, status 변화(S4·S5), 같은 기술의 새 ADR(`radar.py match` 다시 — S1). 사람의 답: 계속 · 다시 판정 · 버림
4. 항목이 끝나면(채택·기각·거부·버림) **checkpoint thread를 지운다.** 별도 파일은 `history`와 함께 남는다

### 4-1. 지문 (결정 7)

- **무엇을**: ① ADR repo `docs/adr/*.md` 전체 ② 대상 repo CLAUDE.md의 스택 절(「의존성 → component」·「외부 모델·서비스」) — 초안의 `affected`가 이 매핑에서 나오므로 대기 중에 대상 repo 의존성이 바뀌면 초안이 낡는다
- **기록용 칸은 뺀다**: `revisit_last_checked` · `last_determined` 같은 기계가 쓰는 칸. 근거: 매주 월요일 revisit routine이 ADR 파일들에 `revisit_last_checked`를 기록한다(adr PR #1) — 빼지 않으면 대기 중인 모든 항목이 **매주 의미 없이** 다시 승인을 요구하고, 사람은 「계속」을 습관적으로 누르게 된다(결정 3이 무력해진다)
- **왜 전체(A′)이고 관련만(B′)이 아닌가**: 의미 있는 ADR 변화는 드물다(ADR 0010 c1 = 4주에 신규 ADR 1개 이하가 기준일 만큼). 그래서 무관한 변화에 다시 묻는 일도 드물고, 대신 「관련」을 정의할 필요가 없어 놓치는 것이 없다. B′는 `radar.py match`의 문자열 동일성에 기대서 이름이 다른 같은 기술을 놓친다(overview §4 틈 ③)
- **많이 알려 주다가 거슬리면 끈다** (사용자): B′(관련만)로 바꾸는 스위치를 설정으로 둔다. 바꿀지는 재개 중 지문이 달랐던 비율과 그때의 답(§7 측정)을 보고 정한다
- 기각: 원래의 (A) 전체 해시 · (B) 관련 해시 — 둘 다 기록용 칸에 반응한다

checkpoint DB를 통째로 잃으면: 별도 파일이 있는 항목은 파일의 `lifecycle`에서 다시 시작한다(그 단계의 판정을 다시 돈다). 별도 파일이 없는 항목(승인 전)은 사라진다 — 다시 수집·대화하면 된다. **결정 1이 지켜지는지 확인하는 시험이 이것이다.**

## 5. 쓰기 — write-ahead (결정 4)

승인된 쓰기는 두 곳(ADR 파일 · 별도 파일)을 건드리고, 둘을 한 번에 바꿀 방법이 없다. 그래서 원자적으로 쓸 수 있는 한 곳(별도 파일 한 번 쓰기)에 의도를 먼저 남긴다. 원리는 공부 노트 「Write-ahead」.

1. 번호를 정한다 (`radar.py next-id` — 쓰는 이 순간에)
2. 별도 파일에 **의도**: `write_intent: {adr: "0011", path, content_hash, state: intended}`
3. ADR 파일을 쓰고 `radar.py validate`
4. 별도 파일에 **완료**: `state: done`, `adr: "0011"`, `history`에 한 줄

| 어디서 죽었나 | 재개가 보는 것 | 하는 일 |
|---|---|---|
| 2 전 | 의도 없음 | 승인 대기 그대로 — 아무 일도 없었다 |
| 2와 3 사이 | 의도, 0011 파일 없음 | 0011을 쓴다. 그 사이 다른 것이 0011을 가져갔으면 번호를 다시 정하고 의도를 고친다 |
| 3과 4 사이 | 의도, 0011 파일 있음 | 해시가 같으면 완료만 적는다 · **다르면 사람이 고친 것 → 덮지 않고 보인다** (결정 1) |
| 4 뒤 | 완료 | 넘어간다 |

- **구현에서 정한 것 (2026-10-06, HYO-44 구현)**: 의도에 해시만이 아니라 **본문(`content`)도** 남기고 완료되면 지운다 — 「2와 3 사이」 회복에서 쓸 내용이 필요한데 checkpoint에 기대면 결정 1(checkpoint는 잃어도 되는 것)과 어긋난다. ADR 파일은 없을 때만 만든다(`x` 모드) — 덮어쓰기가 구조적으로 안 된다
- 승인 화면에는 번호 대신 「번호는 저장할 때 정해짐」
- validate 실패(3)는 쓰기 실패가 아니라 내용 문제다 — 스킬처럼 그 파일을 고쳐 쓰는 길(repair)이 필요하다 (§8 Q4)

### 5-1. edit (결정 6)

- 사람이 고친 초안이 **쓰일 내용**이다. write-ahead 의도의 `content_hash`는 고친 뒤의 내용으로 계산한다 — 그래야 §5 표의 「해시가 같으면 완료」가 맞게 돈다
- 고친 초안도 쓰기 전에 `radar.py validate`를 지난다. 사람이 고쳤다고 형식 검사를 건너뛰지 않는다. 실패하면 쓰지 않고 오류를 보여 다시 고치게 한다 (모델 repair가 아니라 사람에게 돌려준다)
- edit으로 바꿀 수 없는 것: `status`(R8 — 초안은 늘 `proposed`, status는 ADR 파일에서 사람이 바꾼다) · 번호(쓸 때 정한다, 결정 4). 화면에 칸이 없다
- `history`에 원래 초안의 해시와 고친 초안의 해시를 둘 다 남긴다 — 「모델 초안을 사람이 얼마나 고쳤나」가 실사용 관찰 지표가 된다 (초안 품질)
- 구현: LangGraph `HumanInTheLoopMiddleware`의 `allowed_decisions`에 `edit`을 더한다. 스파이크에서 뺀 이유는 Agents SDK 짝 비교였다(`product/spike/langgraph_spike/README.md`) — 제품은 비교 모드 LangGraph만이라 그 제약이 없다
- 스킬과의 관계: 스킬 capture도 사용자가 대화로 고칠 점을 말하면 반영한다(텍스트 채널). 제품은 구조화된 edit 채널이다 — 「스킬과의 비대칭」 표에 한 줄 (구현 때)

### 5-2. 내보내기 — 승인 = main에 바로 커밋 (결정 8)

- **capture**: 승인(approve·edit)하면 write-ahead로 로컬에 쓴 뒤 커밋 1개 → main에 push. 승인은 Inbox에서 **한 번**
- **detect**: 초안은 지금처럼 로컬에 쓰되(eval 그대로) **Inbox에서 사람이 검토하면** 그때 커밋·push. 스킬에서 「PR 머지 = 검토」였던 자리를 「Inbox 검토」가 이어받는다. 검토 안 된 초안은 main에 쌓이지 않는다
- **왜 PR이 아닌가**: 제품이 시험하는 가설이 G4 「한곳에 모인 통합 UX」(판정문 반대 논거 E)다. Inbox 승인 + GitHub PR 머지는 결정을 두 곳으로 쪼개 가설을 시험하기 전에 제품을 스스로 약하게 만든다. 실사용 지표도 제품 쪽은 앱 이벤트로 잰다(비교 프로토콜 §7)
- **안전장치**
  - 경로 허용 목록: **새** ADR 파일(`docs/adr/NNNN-*.md`)과 `.radar/items/` 아래만 커밋한다. 기존 ADR 파일은 못 고친다(쓰기도 `x` 모드)
  - **fast-forward push만**. 그 사이 사람이 push했으면 pull한 뒤 **재개 검사(§4)를 다시 돈다** — push 충돌은 「세상이 바뀌었다」는 뜻이다
  - 승인 하나 = 커밋 하나. git 이력이 감사 기록이고 되돌리기는 `git revert`
  - eval·dry-run에서는 내보내지 않는다(지금의 no-op Exporter)
- 기각: 항목마다 브랜치 + PR(승인 두 번) · 모아서 PR(승인과 반영 사이가 벌어지고 승인 두 번은 같다)
- **변경 (2026-10-27, 사용자 — 데스크톱 실사용 모드, HYO-99 3단계)**: 「기존 ADR 파일은 못 고친다」의 예외 하나 — revisit 직후 `revisit_last_checked`(기록용 칸, §4-1 A′가 지문에서 빼는 칸)**만** 바뀐 기존 ADR은 승인 없이 커밋 1개로 main에 push한다(`GitExporter.publish_record` · `hitl.export_record`). 이유: 안 남기면 다음 revisit이 같은 조건을 처음처럼 다시 보고 「달라짐」 판정이 흔들린다. 스킬은 이 칸을 PR로 남겼다. 안전장치: 추적 중인 ADR · 수정(M)만 · sync 뒤 HEAD와 파싱해 비교해 기록용 칸 밖(status·본문·다른 칸)이 바뀌었으면 거부(작업 사본에 남김) · dry-run이면 no-op (변이 6개, `test_export.py`)
- **구현에서 정한 것 (2026-10-06, 사용자)**: ① 제품이 **같은 실행에서 직접 내보낸** 변화(같은 실행의 다른 초안이 main에 들어간 것)는 지문 비교에서 넘긴다 — 우리가 만든 변화는 바깥 세상의 변화가 아니다. 안 그러면 detect 초안을 연달아 승인할 때 둘째부터 매번 「낡음」이 뜬다 ② 거부(reject)한 항목의 닫힌 기록(`.radar/items/…yaml`)도 커밋한다 — git 이력이 감사 기록 ③ 내보내기 스위치는 셸 환경 변수 `RADAR_EXPORT=git`(기본 꺼짐)

## 6. thread (결정 5)

- `thread_id = item-id`. checkpoint와 별도 파일이 1:1
- 대기 중인 thread는 자동 만료하지 않는다. Inbox(HYO-51)에 **대기 일수**를 보인다
- 끝난 항목의 checkpoint는 지운다 — 그래프 상태는 재현용이 아니라 진행용이다. 무엇이 있었는지는 별도 파일 `history`와 ADR 파일·git 이력이 남긴다
