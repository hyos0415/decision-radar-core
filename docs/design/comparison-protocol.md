# 스킬 ↔ 제품 비교 규칙

> v1 · **2026-09-29 등록** (등록 커밋이 증거) · 상위 문서: `overview.md` (§3 두 구현, §4 틈 분석, §10 일정)
> 이 문서는 **결과를 보기 전에** 비교 방법과 판정 규칙을 고정한다. 결과를 보고 규칙을 바꾸면 그 비교는 탐색적 결과가 된다.

## 1. 원칙

1. **허술한 기준선을 이기는 제품은 증거가 아니다.** 스킬로 고칠 수 있는 틈(overview §4 왼쪽 열)은 스킬에서 먼저 고친다
2. **같은 조건에서만 비교한다** — 같은 모델, 같은 픽스처, 같은 채점, 같은 안전 규칙층(`radar.py`)
3. **역수입 규칙**: 제품을 만들다 찾은 개선이 스킬에도 적용 가능하면 **스킬에도 넣는다**(또는 넣지 않은 이유를 기록한다). 제품에만 넣으면 그 차이는 구조의 차이가 아니라 작업량의 차이다
4. **판정 규칙은 지금 정한다** (§8). 결과를 본 뒤 기준을 옮기지 않는다

**역수입 적용 (2026-10-02, 사용자 결정) — 수집 파이프라인 (E9)**: 제한된 출처 풀의 주간 스냅숏(HYO-72)은 스크립트라 스킬의 detect도 읽을 수 있다(`radar.py snapshot feed` 자리). 다만 10/5~11/1 실사용 기준선 도중에 스킬을 바꾸면 기준선이 흔들린다. 그래서:
- **실사용 4주 기준선은 `skill@v1` 그대로** 돈다 (detect = 웹 검색)
- 수집기가 완성되면 detect가 같은 스냅숏을 읽는 **`skill@v2`**를 만들고, **v1 ↔ v2 짝 eval 비교를 따로** 한다 — 출처 풀 자체의 효과를 스킬 안에서 잰다
- 제품(11/2~)과 `skill@v1` 실사용 비교의 차이에는 출처 풀 효과가 섞여 있다. 판정문에 이 한계를 적고, v1 ↔ v2 결과로 풀 효과를 따로 보고한다

## 3. 비교 모드 — 고정 조건

| 조건 | 값 |
|---|---|
| 모델 | 스킬과 제품 모두 **같은 Claude 모델·같은 effort** (overview §7 비교 모드). 멀티 모델(최적화 모드)은 이 비교에 넣지 않는다 |
| 버전 | 스킬 `skill@vN`, 제품 `app@vN`을 git tag로 고정. 비교 결과에는 두 tag를 함께 적는다 |

| 격리 | 제품도 정답지·레포 경로에 닿지 않는다. `answer_key_access`를 제품 trace에도 적용 |

| 사용량 | 스킬은 구독(`claude -p`), 제품은 API. 비용은 **토큰 수**로 나란히 두고, 달러는 둘 다 API 단가로 환산 |

**변경 (2026-10-26, 사용자 결정 — HYO-99 실행 엔진)**: 위 「사용량」 줄의 「제품은 API」를 바꾼다. 제품의 **detect·revisit 주 엔진도 구독 `claude -p`**(`engines.ClaudeCliRunner` — 같은 모델 `claude-sonnet-5-5` · 같은 effort `medium`, 읽기 MCP 도구만)이고, **capture만 API**다(HITL 2턴이라). 그래서 실사용 비교에서 두 도구는 같은 실행 방식(구독 CLI)으로 돈다 — 모델·effort 고정 조건(위 「모델」 줄)은 그대로 지켜진다. 비용 비교는 여전히 토큰 수가 기준이고, 구독 실행의 달러는 CLI가 알려 주는 정가 환산(`cost_usd_equiv`)으로 둔다(실제로 낸 돈이 아니다). eval의 짝 비교(§4)는 `run_eval.py --engine api|claude-cli`로 엔진을 명시해 돌리고 결과에 엔진을 적는다.

## 4. 공용 eval 어댑터

기존 러너(`eval/runner`)가 스킬을 채점하는 방식을 **구현과 무관한 계약**으로 바꾼다.

```
입력:  작업 디렉터리 (ADR repo · 대상 repo · 스냅숏 · served.log) + flow + now + payload
출력:  run_report JSON (references/schema.md) + 작업 디렉터리의 최종 상태 + 도구 호출 기록
```

- **스킬 어댑터** = 지금 러너 (`claude -p` transcript → 도구 호출 기록)
- **제품 어댑터** = 제품 API를 부르고, **제품의 trace를 같은 도구 호출 기록 형식으로** 변환
- 채점(expected·INV-1~8·격리 검사)은 어댑터 뒤에서 **한 코드로** 돈다 — 채점기가 두 벌이면 비교가 아니다
- capture의 2턴(미리보기 → 승인)은 제품에서 **HITL interrupt → resume**으로 대응한다. 어댑터가 두 번째 턴을 resume 호출로 바꾼다

## 5. 시간축 시나리오 (새 eval 유형)

지금 eval은 케이스당 **1회 실행**이다. 여러 주에 걸친 흐름은 원리상 못 잡는다(틈 ①). 두 구현 모두에 새 유형을 만든다.

시나리오 = **주 단위 실행의 연쇄**. 주마다 스냅숏이 바뀌고, 주 사이에 사람의 행동이 끼어든다. 기대 결과는 주마다 있다.

| 시나리오 (예) | 흐름 | 보는 것 |
|---|---|---|
| **재알림** | W1 met(알림) → W2 undetermined(403) → W3 met | W3에 알림이 **다시 나가지 않는가** (틈 ①) |
| **사람의 결정** | W1 met(알림) → 사람이 status를 `revisit`로 → W2 확인 | status 변경을 존중하고 확인 범위를 맞게 바꾸는가 (R8·R13) |
| **ADR 추가** | W1 → capture로 새 ADR 승인 → W2 revisit | 새 ADR이 첫 실행 규칙(R15)으로 들어오는가 |
| **실험 대기** | detect 후보 → 실험 제안 → 사람 승인 → (며칠) → 결과 도착 → 기록 | 대기 상태를 잃지 않고 이어지는가 (**G5**) |
| **중복 알림 폭주** | 같은 조건이 5주 연속 met | 알림 1건으로 끝나는가 (R3) |

- 스킬은 상태를 **ADR 파일에만** 남긴다 → 파일에 없는 상태(대기, 알림 이력)는 다음 주에 없다. 이게 스킬 구조의 실제 한계인지, 스키마에 필드 하나 추가로 고칠 수 있는지(역수입)를 이 시나리오가 가른다
- 실험 대기 시나리오는 스킬에 대응 흐름이 없다. 스킬은 **"PR을 열고 끝"**으로 채점하고, 이 차이는 결과에 "스킬 미지원"으로 적는다 — 실패로 세지 않는다
- 시나리오는 `eval-precondition` 모드 1로 전제를 확정한 뒤 만든다

## 6. 규모 비교 (G1)

Retrieval Arena의 규모 티어(`retrieval-arena.md` §2)를 end-to-end에 쓴다.

| 티어 | 스킬 | 제품 |
|---|---|---|
| T0 (실제 규모) | Full Context | Arena에서 고른 전략 |
| T1 · T2 (합성 50·500) | Full Context — 컨텍스트·비용이 어디서 무너지나 | 같은 전략 |
| T3 (컨텍스트 한도 밖) | 실행 불가로 기록 | 같은 전략 |

- 재는 것: 통과율 · 안전 pass^k · 입력 토큰 · wall time · **틈 ③(동일 결정 찾기, K 유형)**의 정답률
- 제품의 검색 전략은 **Arena test 결과로 고른 뒤 고정**한다 — 규모 비교를 보면서 전략을 바꾸지 않는다
- 판정의 핵심 산출물: **"스킬이 무너지는 규모"** — 통과율이 떨어지기 시작하는 티어, 또는 비용이 제품을 넘어서는 티어

### 같은 주 재생 (2026-11-03 등록, HYO-163 — 결과 전)

실사용 비교는 **사람의 행동**을 잰다. 재생은 그걸 대신하지 않고, 다른 질문에 답하는 두 번째 증거다 — **같은 주 입력에 두 체계는 무엇을 냈고, 어디서 갈렸나.** 스킬(실행할 때 웹을 찾는다)과 제품(매주 모아 얼리고 거른다)은 같은 일을 하는 다른 체계라서, 결과가 같아도 무엇을 놓치는지가 다르다. **G4 판정(§8 실사용 줄)에 쓰지 않는다.**

- **대상**: 그 주 스킬이 실제로 낸 detect와, 그 실행 **전에** 얼린 마지막 코퍼스를 짝짓는다 — 10/12 ↔ corpus@2026-W41(10/6), 10/19 ↔ W42(10/13), 10/26 ↔ W43(10/20)
- **제품**: HYO-162 머지 뒤 main(429d9e5)으로 고정한다. 재생 중 코드를 고치면 등록 위반이다 — 고쳐야 하면 「변경」으로 남기고 전 주차를 다시 돌린다. 관문은 세 주 모두 이 코드로 다시 돌리고, W43은 얼려 둔 관문 결과(radar-snapshots `detect/2026-W43`)도 참고로 함께 적는다

### 같은 순간 짝 — 스킬 그림자 (2026-11-03 등록, HYO-166 — 결과 전)

재생은 과거 스킬 실행을 다시 돌릴 수 없어 「월요일 아침 스킬 ↔ 지난 화요일에 얼린 코퍼스」로 짝짓는다 — 6일 시점 차이가 섞이고, 그 일부는 재생 설계가 만든 차이다(실제 제품 운영은 화 16:00 수집 → 18:00 detect). 같은 순간에 두 체계를 돌리면 시점 차이가 사라지고 **체계 차이(출처 범위 · 거르는 방식 · 모델 판단)만** 남는다. 사용자 판단(11/3): 두 체계는 탐지할 수 있는 게 달라서 취사선택이 아니라 **함께 돌려 범위를 넓히는 것**이 이상적이다 — 이 짝은 그 합집합 운영이 값어치가 있는지를 재는 자료다.

- **언제**: 제품 정기 detect(11/10 W46 · 11/17 W47)가 끝난 직후, 같은 기기(맥)에서 스킬 detect를 한 번 돌린다. 정기 실행이 아닌 손 실행 · 건너뛴 실행에는 붙이지 않는다
- **스킬**: `skill@v1` 라이브 모드(웹 검색) · 같은 모델 `claude-sonnet-5-5` · 같은 effort `medium` · 실행 루트는 eval 러너처럼 스킬만 복사한 빈 폴더 + 제품이 그 실행에서 읽은 것과 같은 ADR 사본
- **그림자다**: PR · issue · 알림 · Inbox · 실사용 행동 로그(`events.jsonl`)에 아무것도 쓰지 않고, ADR repo 원격에 닿지 않는다. 출력과 transcript는 `<data>/shadow-skill/<주>/`에만. API 그림자(위 HYO-99 변경)와 같은 자리라 §9 「두 도구를 같이 켜기」에 해당하지 않는다
- **봉인**: 사용자는 **11/22까지 그림자 출력을 보지 않는다** — 스킬이 찾은 것을 알면 제품 초안 검토가 달라져 실사용 비교가 오염된다. 실행 성공 · 실패만 확인한다. 그림자가 실패해도 제품 실행은 그대로다(실패 이유를 기록)
- **지표**: 재생과 같다 — 주별 「둘 다 · 스킬만 · 제품만」, 갈린 항목의 단계, 같은 항목 기준(정규화 패키지 이름 + 릴리스 주 버전). 「수집 시점」은 「제품 detect 입력의 수집 시각 이후에 나온 릴리스」로 판정한다
- **반복**: k=1 — 같은 순간은 반복할 수 없다. 두 주 · 두 짝이라 스모크 수준이고, 결과에 그렇게 적는다
- **합집합 판단 자료**: 각 체계만 잡은 항목을 관찰로 보고한다(문턱 없음 — 비용 축처럼 관찰). G4 판정에는 쓰지 않는다. 합집합 운영 여부는 실사용 판정(11/24 무렵) 뒤에 이 자료와 재생 결과를 보고 따로 정한다

## 8. 판정 규칙 (결과 전에 고정)

| 축 | 제품이 "낫다" | 제품이 "같다" | 제품이 "못하다" |
|---|---|---|---|
| **안전** | — (안전은 이기는 축이 아니다) | 안전 케이스 pass^k **전부 통과** | **하나라도 실패 → W4 게이트 불통과**, 실사용으로 가지 않는다 |
| 정확 | 짝지은 통과율 차이의 95% CI가 0보다 위 | CI가 0을 포함 (비열등) | CI가 0보다 아래 |
| 비용 **(관찰만)** | 같은 통과율에서 토큰 ≤ 스킬의 80% | 80~120% | > 120% |
| 시간축 | 스킬이 틀린 시나리오를 제품이 맞힘 (역수입 후에도) | 역수입으로 스킬도 맞힘 | 제품이 틀림 |
| 규모 | 스킬이 무너지는 티어에서 제품이 통과 | 모든 티어에서 둘 다 통과 | — |
| 실사용 | 알림 대비 행동률·후보 대비 검토율이 **둘 다** 높음 | 한쪽만 높거나 비슷 | 둘 다 낮음 |

- **비용은 관찰 지표다 (2026-09-29 결정).** 80%·120%는 결과를 묘사하는 구간일 뿐, 제품의 채택·기각 판정에 쓰지 않는다 — "비용이 이만큼 들었다"는 관찰 자체가 의미 있다. 구간 값은 임의로 정했고, 결과를 보고 옮기지 않는다
- 정확 축의 CI는 케이스가 독립 표본이 아니라서(사례 3개의 변형) **넓게 나올 것**이다. "같다"가 가장 가능성 높은 결과이고, 그것도 결론이다

**변경 (2026-11-07, 사용자 결정 — HYO-57, 실사용 줄의 질문을 바꾼다)**: 위 표의 **실사용 줄로 스킬과 제품 중 어느 쪽이 나은지 판정하지 않는다** — 11/24 무렵의 G4 판정(§7 HYO-163 변경의 「판정은 그 뒤」)은 내지 않는다. 묻는 질문은 **「두 체계를 합치면 각자 혼자일 때보다 더 잡나」**로 바뀐다. 답은 §7 「같은 순간 짝」(11/10 W46 · 11/17 W47)과 「같은 주 재생」(W41~W43) 자료로 내고, **11/23에 합집합 운영 여부를 정한다**(`union-pipeline.md` §8 일정, HYO-167). §7 그림자 절의 「합집합 운영 여부는 실사용 판정(11/24 무렵) 뒤에」는 「실사용 판정 없이 11/23에」로 읽는다.
- **이유 (사용자)**: 두 체계는 찾는 방법이 달라 출처부터 다르다 — 스킬은 실행할 때 웹을 찾고, 제품은 매주 정한 출처를 모아 얼린 뒤 거른다. 하나를 골라 쓰는 게 아니라 합치는 쪽이 결론이라 「어느 쪽이 나은가」는 물을 이유가 없어졌다. 원래 판정도 약했다 — 스킬 3주와 제품 3주는 다른 주라 들어온 소식부터 달라, 행동률 차이가 도구 차이인지 가를 수 없다(위 교란 표 「두 기간의 소식량이 다르다」)
- **판단 때 본 근거** (스킬 기간 기록과 놓친 소식 추적 — 같은 순간 짝 결과가 아니다):
  - 스킬이 잡아 사람 결정까지 간 것: Langfuse Python SDK v5(10/19 detect 초안 0015 → 채택, adr PR #13) · Anthropic Python SDK v2(10/26 detect 초안 0016 → 채택, adr PR #16 · #17) · Claude Haiku 5.5(10/12 revisit 알림 adr issue #7 → 재측정 · ADR 0007 Luna 유지, adr PR #14). 수집 쪽이 이 셋을 왜 detect로 못 올렸는지는 재생(HYO-164)이 단계별로 가른다
  - 놓쳤을 때 남는 것이 다르다: 수집은 무엇을 모았고 어느 단계에서 왜 뺐는지가 남아(`trace.jsonl`, HYO-171) 놓친 것을 찾아 고칠 수 있다. 스킬은 결과(초안)만 남긴다 — 무엇을 봤고 무엇을 안 봤는지 기록이 없다
  - GPT-6.1 Terra는 스킬이 놓친 것이 아니다: 마지막 스킬 detect가 10/26 09:38(KST, adr PR #16)이고 첫 출시 기록은 10/27 02:58(KST, HN 첫 글)이다. 11/2부터는 비교 규칙대로 스킬 routine을 껐다. 수집은 W44 · W45에 모으고도 놓쳤다가 고쳤다(`docs/decisions/2026-11-04-missed-items.md`, HYO-168)
- **그대로인 것**:
  - 실사용 기간 운영 — 제품 기간 11/2~11/22 · 스킬 routine 꺼짐 · §9 「실사용 기간에 두 도구를 같이 켜기」 금지. 합집합은 11/23 판단 뒤에만 켠다
  - 같은 순간 짝 · 재생의 규칙 — 그림자 출력 봉인(11/22까지) · 반복 횟수 · 같은 항목 기준 · 「둘 다 · 스킬만 · 제품만」 · 갈린 단계. 합집합 판단에는 문턱을 두지 않는다(관찰)
  - §7 「기록하는 것」의 지표는 계속 남긴다(행동 로그는 앱이 쓴다). 11/24 무렵에는 **관찰로만** 보고하고 낫다 · 같다 · 못하다를 매기지 않는다
  - 안전 · 정확 · 비용 · 시간축 · 규모 줄의 판정 규칙
- **H절 연결**: 실사용 판정에 기대는 두 줄 — 「Skill로 축소」 · 「반대 논거 E 성립 → Custom Product 재판정」 — 은 이 판정으로 정하지 않는다. 반대 논거 E(통합 UX가 가치)는 실사용 비교로 검증하지 않은 채 남고, 판정문에 그렇게 적는다. 도구를 견주지 않는 두 줄(「두 기간 모두 새 ADR이 거의 없다」 · 「알림 대부분이 두 기간 모두 무시된다」)은 기록한 지표로 그대로 읽는다
- **정한 시점**: 11/7 — 스킬 기간 4주와 제품 기간 detect 초안 두 건(adr PR #18 close · #19)이 나온 **뒤**, 같은 순간 짝 첫 실행(11/10) **전**이다. 문서에는 11/11에 남긴다 — 그 사이 11/10 짝이 돌았어도 출력은 11/22까지 봉인이다(§7). 제품 기간의 중간 비율은 보지 않기로 했다(11/3)

### 판정문 H절과의 연결

| 결과 | 의미 (판정문 H절) |
|---|---|
| 두 기간 모두 새 ADR이 거의 없다 | **프로젝트 중단** 신호 — 쓸 결정이 없으면 문제 가설이 틀렸다 |
| 스킬 기간에 기록이 쌓이고, 제품이 실사용에서 낫지 않다 | **Skill로 축소** (원 판정 유지) |
| 제품이 실사용에서 낫고, 원인이 "한곳에 모임"으로 일지에 나온다 | 반대 논거 **E 성립** → Custom Product 재판정 근거 |
| 알림 대부분이 두 기간 모두 무시된다 | **다른 문제로 pivot** — 재검토가 병목이 아니다 |
| 규모에서 스킬이 무너지고 제품의 검색이 그걸 고친다 | G1·G2의 답 — Retrieval Arena가 제품의 정당한 이유 |
